# Контекст проекта yandex-disk-copy

Документ для модели, которая продолжает работу с репозиторием без предыдущей переписки. Факты ниже сняты с кода на коммите `03f820c` и с проверок 9 октября 2026. Чего в источнике нет, здесь нет.

Читатель должен понять, что инструмент делает, чем опубликованное состояние отличается от локального, и какие решения уже приняты.

## Что это

Веб-обёртка на FastAPI вокруг копирования файлов между Дисками сотрудников Яндекс 360. Интерфейс — форма и живой лог по SSE. Процесс копирования на Диск получателя идёт через API Диска, не через браузер.

Репозиторий: <https://github.com/cromovsky/yandex-disk-copy>, ветка `main`.

Два образа:

| Образ | Сборка | Что умеет |
|---|---|---|
| `cromovsky/yandex-disk-copy-v2` | `CROSS_ORG_ENABLED=1` | одна организация и перенос между организациями |
| `cromovsky/yandex-disk-copy` | `CROSS_ORG_ENABLED=0` | только одна организация; режим «между организациями» в UI скрыт |

Локальный `docker-compose.yml` собирает образ сам (`build: .`) и не скачивает тег с Docker Hub. `docker-compose.caddy.yml` берёт готовый `cromovsky/yandex-disk-copy:latest`, то есть образ v1.

## Что видит пользователь

Адрес локального контейнера: <http://localhost:8000>.

В карточке источника и назначения две вкладки: «Один диск» и «Несколько дисков». Кнопка «Сохранить локально» есть только на «Одном диске», в обоих режимах организации. На пакетной вкладке её нет.

Пакет: до 25 записей, одновременно 5 переносов. Шаблон пар — `/static/pairs-template.csv` (`SOURCE;DESTINATION`). Для общего диска шаблон только источников — `/static/sources-template.csv`; все источники идут на один общий диск, нужны один `DESTINATION` с правом записи и общий `VD_HASH`. PATH, тип назначения и `VD_HASH` общие на весь пакет.

Поля: `CLIENT_ID`, `CLIENT_SECRET`, `ORGID`, `ADMIN_TOKEN`, email источника, тип назначения (личный Диск или общий диск), email получателя, `VD_HASH`, `PATH` (`/` — корень), `PAGE_LIMIT` (по умолчанию 1000).

Повторный перенос не обновляет файл, который у получателя уже есть под тем же именем. Ответ 409 считается успехом: в логе «уже существует, пропускаю», в счётчике `saved`. Содержимое под тем же именем не перезаписывается. Обход при повторе полный, не «только то, что в прошлый раз упало».

Полный список ошибок джоба — `GET /api/run/<job_id>`, поле `fails`. В лог попадают первые 50 (`FAILS_LOG_LIMIT`).

## Учётные данные

Два разных набора, их не смешивать.

Сервисное приложение организации выпускает токен сотрудника через token-exchange:

`POST https://oauth.yandex.ru/token`

Параметры: `grant_type=urn:ietf:params:oauth:grant-type:token-exchange`, `subject_token_type=urn:yandex:params:oauth:token-type:email`, `subject_token` — email, плюс `client_id` и `client_secret`. Срок в коде: `expires_in` минус 100 секунд, затем токен запрашивается снова. В лог пишется `scope` выданного токена. Для API 360 код берёт идентификатор сотрудника как второй сегмент access token между точками (`token.split(".")[1]`).

Права приложения на Диск: `cloud_api:disk.read`, `cloud_api:disk.write`, `cloud_api:disk.info`. Сверка места требует `disk.info`. Копирование и скачивание идут на `disk.read` и `disk.write`.

`ADMIN_TOKEN` — отдельное OAuth-приложение с `directory:read_users` и `directory:write_users`. Если он задан и сотрудник-источник заблокирован (`isEnabled: false`), инструмент на время работы включает его и в `finally` выключает обратно. Если вернуть блокировку не удалось, в логе строка `ВНИМАНИЕ` с просьбой заблокировать сотрудника вручную. В режиме между организациями админ-токен есть только у источника. Без `ADMIN_TOKEN` проверка блокировки пропускается.

Ошибка `400` с `unauthorized` при выпуске токена чаще всего значит, что OAuth-приложение не зарегистрировано как сервисное в организации. Регистрация: `POST https://api360.yandex.net/security/v1/org/<ORGID>/service_applications`.

## Куда попадают файлы при переносе

Личный Диск получателя: папка `disk:/<email источника>`, оригинальные имена. Верхний уровень `PATH` публикуется и сохраняется целиком: папка уезжает как папка, а не как россыпь файлов.

Общий диск: `vd:<hash>:disk:/<email источника>/…`, дерево файлов сохраняется. `VD_HASH` — метка из адреса Диска после `vd/`. Без неё перенос на общий диск не стартует.

Код личного сохранения передаёт в `save-to-disk` параметр `save_path`. Из-за него файлы оказываются в `disk:/<email источника>`. В названии публичного метода документации фигурируют «Загрузки»; на фактическую папку этого переноса ориентироваться по одному названию метода нельзя.

## Как копируется личный Диск

Методы `make_links`, `get_links`, `save_links`.

1. `PUT /v1/disk/resources/publish` по элементам `PATH`.
2. Повторное чтение метаданных, сбор `public_key`. Нет ключа — запись в `fails`.
3. `PUT /v1/disk/resources` — создать папку получателя. 201 — создана, 409 — уже есть.
4. `POST /v1/disk/public/resources/save-to-disk` с `public_key`, `name`, `save_path`. 201 — готово. 202 — ждать операцию. 409 — уже есть, это `saved`.

`POST /v1/disk/resources/copy` этот инструмент не вызывает.

Если `save-to-disk` отвечает 404, для файла есть запасной путь. Для папки его нет: папка остаётся в `fails`.

Повторный `publish` того же пути возвращает тот же `public_key`. Если публичная ссылка мертва, повторная публикация её не чинит. Публичное скачивание `GET /v1/disk/public/resources/download` по этому ключу даёт тот же 404 `DiskNotFoundError`. Файл при этом на Диске есть.

Запасной путь только для файла и только на личный Диск (`_copy_file_bytes`):

1. `GET /v1/disk/resources/download` токеном владельца.
2. Скачать байты.
3. `GET /v1/disk/resources/upload?overwrite=false` токеном получателя. 409 — файл уже есть, загрузка не делается.
4. `PUT` байтов на полученный href.

Весь файл держится в памяти. Порог `DIRECT_COPY_MAX_BYTES` — 512 МиБ. Выше порога копирование этого файла через сервис прекращается с ошибкой. На общий диск этот запасной путь не распространяется.

## Как копируется общий диск

Метод `save_to_shared`. Запасного копирования байтами нет.

1. Рекурсивно собрать файлы под `PATH`.
2. Один раз создать дерево `vd:<hash>:disk:/<email>/…`.
3. На каждый файл: опубликовать, взять `public_key` из свежих метаданных, получить публичный href скачивания, отправить его в `POST /v1/disk/virtual-disks/resources/upload` параметром `url`.
4. Ответ 202 — ждать операцию до 600 с, опрос от 0,5 с до 10 с. 409 — уже есть.

Операции: `GET /v1/disk/operations/<id>` через href из ответа.

## Локальное сохранение

Кнопка скачивает `PATH` одного источника на машину, с которой запущен контейнер. Получатель, тип назначения и `VD_HASH` не нужны. Эндпоинты: `POST /api/save-local` и `POST /api/save-local-cross`.

Внутри контейнера каталог — `LOCAL_SAVE_DIR`, в образе и в локальном compose это `/downloads`. На хост его выводит том `./downloads:/downloads`. В логе для человека путь берётся из `LOCAL_SAVE_HOST_DIR` (по умолчанию `./downloads`) и дописывается email. Эта строка относительная и стоит выше `COMPLETED`, поэтому по одной финальной строке место файлов не видно.

Файлы на хосте при запуске из этого репозитория:

`/Users/dpigulevskiy/Documents/yandex-disk-copy/downloads/<email>/…`

9 октября 2026 сохранение `dpigulevskiy@pilot.360sandbox.ru` с `PATH=/` завершилось `saved: 13, fails: 0`, около 520 МБ, каталог именно этот.

Обход создаёт каталоги и список файлов. Файл пропускается, если локальная копия уже есть и `st_size` совпадает с `size` на Диске. Иначе: `GET /v1/disk/resources/download`, затем потоковая запись во временный `имя.part` кусками по 1 МиБ и `os.replace`. В коде локального сохранения нет порога размера: 25 ГБ и 50 ГБ этим путём не отсекаются. Нужно свободное место на диске хоста. Если запись падает, `finally` удаляет `.part`; при следующем запуске файл качается сначала. Потолок 512 МиБ к этой кнопке не относится.

Путь с `..` или `\` не записывается: он попадает в `fails` с текстом «Небезопасный путь». Если `/downloads` не является томом, в логе предупреждение, что файлы останутся внутри контейнера.

Разблокировка источника при заданном `ADMIN_TOKEN` для локального сохранения тоже выполняется.

## Лимиты запросов

Лимит API Диска, который инструмент держит сам: на один IP и один клиент 40 запросов/с на чтение и 5 на изменение. Заголовков `X-RateLimit-*` API не отдаёт. Полоса одна на процесс.

Чтение — методы `GET`, `HEAD`, `OPTIONS`: список, метаданные, ссылка на скачивание и само тело файла. Изменение — остальные методы: публикация, создание папки, `save-to-disk`, загрузка. Неизвестный метод считается изменением.

Ответ 429 ставит общий барьер на обе полосы. `Retry-After` понимается как число секунд и как HTTP-дата. Пауза не длиннее 120 с. 409 и 507 не повторяются. 500, 502, 503, 504 повторяются без общего барьера, до 5 попыток.

Переменные окружения, значения по умолчанию в коде и в Dockerfile:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `DISK_API_READ_RPS` | 40 | темп чтения |
| `DISK_API_WRITE_RPS` | 5 | темп изменения |
| `DISK_API_RPS` | не задана | старая ручка: задаёт темп чтения; изменение при этом не выше 5 и не выше этого значения |
| `HTTP_TIMEOUT_SEC` | 120 | второй элемент таймаута requests; первый, на соединение, в коде равен 10 с |
| `SPACE_CHECK` | не задана | `1` включает сверку свободного места до переноса |
| `LOCAL_SAVE_DIR` | `/downloads` в образе, `./downloads` если переменной нет и процесс запущен без Docker | каталог записи внутри процесса |
| `LOCAL_SAVE_HOST_DIR` | `./downloads` | строка в логе, не путь внутри контейнера |
| `CROSS_ORG_ENABLED` | `1` | `0` скрывает режим между организациями |

Строка `RATE LIMIT | чтение: 40…` в начале лога — не ошибка. Это отметка темпа.

Сверка места по умолчанию выключена (`SKIP_SPACE_CHECK`). Раньше отсутствующее поле `used_space` давало `KeyError`, а 403 на `GET /v1/disk/` молча заканчивался нулём файлов. Сейчас отказ доступа на Диске поднимается как `CopyError`. Включить сверку: `SPACE_CHECK=1`. Она ходит в `GET /v1/disk/` и для общего диска в `GET /v1/disk/virtual-disks`.

## Запуск

Локально, из каталога репозитория. Из домашнего каталога compose-файла нет, команда без `-f` отвечает `no configuration file provided`.

```bash
docker compose -f ~/Documents/yandex-disk-copy/docker-compose.yml up --build -d
```

Обновление сервера, который тянет образ с Docker Hub:

```bash
docker compose pull && docker compose up -d
```

Для v2 на сервере в compose должен быть `cromovsky/yandex-disk-copy-v2`, не образ v1. Локальное сохранение на хосте появляется только если смонтирован `./downloads:/downloads`.

Публикация новых образов: отдельные теги, `latest` переключается на них, старые теги не перезаписывать и не удалять. Платформы `linux/amd64,linux/arm64`. Сборщик `multiarch` в OrbStack при публикации 9 октября не резолвил `registry-1.docker.io` через `8.8.8.8`. Сборка прошла временным buildkit с `--dns 1.1.1.1` и `--dns 84.252.160.1`; контейнер после публикации удалён, текущим сборщиком снова оставлен `multiarch`.

## DNS на локальном OrbStack

9 октября контейнер не резолвил `oauth.yandex.ru`: встроенный резолвер `127.0.0.11` форвардил на `1.1.1.1` и `8.8.8.8`, запрос падал с `Temporary failure in name resolution`. Хост имя резолвил. Прямой DNS `1.1.1.1` из контейнера тоже резолвил.

В локальный `docker-compose.yml` добавлены `dns: 1.1.1.1` и `77.88.8.8`. Контейнер пересоздан, после этого из него открылись `oauth.yandex.ru` и `cloud-api.yandex.net`. Эта правка не в git и не в образе на Docker Hub. В `resolv.conf` контейнера по-прежнему `nameserver 127.0.0.11`; меняется список `ExtServers`.

## Что уже решено и не надо переигрывать без новой просьбы

- Сверка места выключена по умолчанию. Включать её флагом, а не требовать `SPACE_CHECK` от пользователя.
- Повторный перенос не обновляет одноимённый файл.
- Байтовый запасной путь — только файл и только личный Диск, не папка и не общий диск.
- Локальное сохранение пишет на хост через том, не в слой контейнера и не в zip браузера.
- Лимит пакета — 25 записей и 5 одновременных переносов.
- При публикации на Docker Hub старые теги сохранять.
- Страницу Wiki не менять, пока об этом не попросят. Черновики в `.wiki-draft/` после прошлой публикации удалены, заново их не создавать.
- Секреты из `~/.zshrc` и `~/.stefania/` не читать. Рекурсивный поиск от корня Arcadia не делать: этот проект — отдельный git-репозиторий.
