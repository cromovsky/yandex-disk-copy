# Yandex Disk Copy — web-интерфейс

[![Docker v2](https://img.shields.io/docker/v/cromovsky/yandex-disk-copy-v2?logo=docker&label=docker%20v2&color=0f7ff0)](https://hub.docker.com/r/cromovsky/yandex-disk-copy-v2)

Веб-обёртка вокруг скрипта копирования файлов с одного Яндекс.Диска на другой.
Использует сервисные приложения Яндекс 360, API Диска и API360 для блокировки /
разблокировки сотрудника.

**Образы в Docker Hub:**
- [`cromovsky/yandex-disk-copy-v2`](https://hub.docker.com/r/cromovsky/yandex-disk-copy-v2) — оба режима (одна организация + между организациями);
- [`cromovsky/yandex-disk-copy`](https://hub.docker.com/r/cromovsky/yandex-disk-copy) (v1) — только режим «одна организация».

📄 **Инструкция для администраторов** (настройка сервисного приложения + запуск
из Docker Hub) — [docs/INSTRUCTION.md](docs/INSTRUCTION.md).

После запуска процессы копирования идут на бэкенде Диска — файлы окажутся в
отдельной папке на Диске получателя (названа по email источника) с оригинальными
именами.

## Что внутри

```
yandex-disk-copy/
├── app/
│   ├── disk_copy.py     — логика копирования (класс DiskCopier)
│   ├── main.py          — FastAPI: форма + запуск + SSE-лог
│   └── static/index.html — UI (форма параметров и живой лог)
├── Dockerfile
├── docker-compose.yml
└── requirements.txt
```

## Запуск в Docker

```bash
docker compose up --build
```

Открыть <http://localhost:8000>, заполнить форму, нажать «Запустить перенос».
Лог выполнения стримится в браузер в реальном времени по Server-Sent Events.

## Запуск без Docker (для разработки)

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

## Параметры формы

| Поле                  | Описание |
|-----------------------|----------|
| `CLIENT_ID` / `CLIENT_SECRET` | сервисное приложение с правами `cloud_api:disk.read/write/info` |
| `ORGID`               | ID организации |
| `ADMIN_TOKEN`         | токен с правами редактирования сотрудников (для блокировки/разблокировки) |
| `SOURCE`              | email сотрудника-источника |
| Тип назначения        | **Личный Диск** или **Общий диск** организации |
| `DESTINATION`         | email получателя; для общего диска — сотрудник с правом **записи** |
| `VD_HASH`             | метка общего диска (из URL после `vd/`), только для общего диска |
| `PATH`                | папка на диске-источнике (`/` — корень) |
| `PAGE_LIMIT`          | размер страницы при обходе (по умолчанию 1000) |
| Список пар / источников | вкладка «Несколько дисков»: до 25 записей, параллельность 5 |

## Пакетный перенос

По умолчанию форма — один SOURCE и один DESTINATION. Для пакета откройте вкладку
**«Несколько дисков»**, скачайте шаблон и загрузите список.

- **Личный Диск** — шаблон пар `SOURCE;DESTINATION` (`/static/pairs-template.csv`).
- **Общий диск** — шаблон только источников (`/static/sources-template.csv`);
  все источники переносятся на один выбранный общий диск. Нужны один
  `DESTINATION` (сотрудник с правом записи) и общий `VD_HASH`.

Максимум **25** записей, одновременно **5** переносов.
PATH, тип назначения и `VD_HASH` общие для всего пакета.

## Логика

1. Получает токен источника через token-exchange по email.
2. Если сотрудник-источник заблокирован — временно разблокирует (и вернёт блок обратно в конце, даже при ошибке).
3. Сверяет занятое место источника со свободным на диске назначения (личный или общий).
4. Публикует ресурсы в `PATH` и сохраняет их на диск назначения:
   - **личный Диск** — через `save-to-disk` в папку `disk:/<email источника>`;
   - **общий диск** — через API `virtual-disks` в папку `vd:<hash>:disk:/<email источника>/…`
     (дерево файлов сохраняется).

## FAQ: токены, права и доступы

Инструменту нужны два разных набора учётных данных: **сервисное приложение**
(для доступа к Дискам сотрудников) и **админ-токен API 360** (для временной
разблокировки сотрудника-источника). Получают их разные роли и по-разному.

### Какое поле формы откуда берётся

| Поле формы | Что это | Откуда |
|------------|---------|--------|
| `CLIENT_ID` / `CLIENT_SECRET` | Сервисное приложение с правами на Диск | Создаёт владелец организации (см. п.1) |
| `ADMIN_TOKEN` | OAuth-токен для API 360 | Выпускает администратор организации (см. п.2) |
| `ORGID` | ID организации | Админка Яндекс 360 или API 360 (`GET /directory/v1/orgs`) |
| `SOURCE` / `DESTINATION` | email сотрудников | Оба должны быть в **одной** организации |

### 1. Сервисное приложение (`CLIENT_ID` / `CLIENT_SECRET`)

**Что это.** Механизм Яндекс 360, позволяющий по API получать временный токен
от имени любого сотрудника организации (обмен токена по его email —
*token-exchange*) и работать с его ресурсами. Именно так инструмент читает Диск
источника и пишет на Диск назначения, не зная паролей сотрудников.

**Кто и на каком уровне создаёт.** Только **владелец организации** — нужно войти
в аккаунт владельца. Требуется настроенный почтовый домен организации.
Подходящие тарифы: Основной / Продвинутый / Корпоративный (новая линейка),
Оптимальный / Расширенный (старая). На организацию — до 20 сервисных приложений.

**Какие права (scopes) выдать** — доступ к Диску:
- `cloud_api:disk.read` — чтение содержимого Диска;
- `cloud_api:disk.write` — запись (сохранение на Диск назначения);
- `cloud_api:disk.info` — информация о Диске (проверка свободного места).

**Обязательный шаг: зарегистрировать приложение как сервисное.** Создать
OAuth-приложение с правами на Диск — недостаточно. Пока оно не внесено в список
сервисных приложений организации, token-exchange возвращает
`400 invalid_request / Unauthorized`. Регистрирует владелец токеном с правом
`ya360_security:service_applications_write`:

```bash
curl --request POST \
  'https://api360.yandex.net/security/v1/org/<ORGID>/service_applications' \
  --header 'Authorization: OAuth <ТОКЕН_ВЛАДЕЛЬЦА>' \
  --header 'Content-Type: application/json' \
  --data-binary '{
    "applications": [
      {"id": "<CLIENT_ID>",
       "scopes": ["cloud_api:disk.read","cloud_api:disk.write","cloud_api:disk.info"]}
    ]
  }'
```

Поле `id` — это client_id приложения. Проверить список — `GET` на тот же URL.
Если функция сервисных приложений ещё не включена, сначала вызвать
`POST .../security/v1/org/<ORGID>/service_applications/activate`.

**Как работает токен.** Инструмент сам выпускает временный токен сотрудника
запросом `POST https://oauth.yandex.ru/token` с
`grant_type=urn:ietf:params:oauth:grant-type:token-exchange`, `client_id`,
`client_secret` и `subject_token=<email сотрудника>`. **Срок жизни токена — 1 час**;
инструмент обновляет его автоматически, если копирование идёт дольше.

> Официальная инструкция:
> <https://yandex.ru/support/yandex-360/business/admin/ru/security-service-applications>

### 2. Админ-токен для API 360 (`ADMIN_TOKEN`)

**Зачем.** У заблокированного сотрудника нельзя выпустить токен Диска. Поэтому
если источник заблокирован, инструмент через API 360 временно разблокирует его на
время копирования и блокирует обратно в конце (даже при ошибке). Для этого нужен
OAuth-токен с правом управления сотрудниками.

**Кто и на каком уровне выпускает.** **Администратор организации**. Это
**отдельное** OAuth-приложение (не сервисное), регистрируется на
`oauth.yandex.ru`.

**Какие права (scopes):**
- `directory:read_users` — чтение данных о сотрудниках (проверка статуса `isEnabled`);
- `directory:write_users` — управление сотрудниками (блокировка/разблокировка).

**Как получить токен.** Зарегистрировать приложение на oauth.yandex.ru, в разделе
«Доступ к данным» указать оба scope, затем открыть под администратором:
```
https://oauth.yandex.ru/authorize?response_type=token&client_id=<ClientID>
```
Скопировать выданный токен — это и есть `ADMIN_TOKEN`. При изменении прав
приложения токен нужно **выпустить заново** (старый сохраняет прежний набор прав).

> Официальная инструкция: <https://yandex.ru/dev/api360/doc/ru/access>

### Частые вопросы

**Почему секреты не зашиты в код, а вводятся в форме?**
Чтобы один и тот же инструмент работал с разными организациями и сотрудниками без
пересборки. Для локального запуска это безопасно (сервис на `localhost`). Для
выноса наружу — вариант с Caddy (TLS + basic-auth) ниже.

**Нужен ли админ-токен, если сотрудник-источник активен?**
Формально инструмент всё равно проверяет статус (`directory:read_users`). Если
источник заведомо активен, разблокировка не выполняется, но токен всё равно
требуется для проверки. Без него шаг проверки статуса упадёт.

**Куда попадают файлы?**
В папку «Загрузки» аккаунта назначения, с префиксом `<email источника>_` в имени.

**Можно ли копировать между разными организациями?**
Нет. Token-exchange работает в пределах организации сервисного приложения —
источник и назначение должны быть в одной организации.

**Принцип наименьших привилегий.** Сервисному приложению не нужны права шире
`cloud_api:disk.*`; админ-токену — шире `directory:*_users`. Не используйте
персональный токен владельца с полным доступом.

## Безопасность

Секреты (`CLIENT_SECRET`, `ADMIN_TOKEN`) вводятся в форме и передаются на
backend. Для локального запуска (`docker-compose.yml`, только `localhost`) это
приемлемо. Для выноса наружу используйте вариант с Caddy ниже — он добавляет
TLS и basic-auth.

## Production-вариант: Caddy (TLS + basic-auth)

`docker-compose.caddy.yml` ставит перед сервисом reverse-proxy Caddy:
сам сервис наружу не публикуется (только `expose`, внутри docker-сети), а Caddy
терминирует HTTPS и требует логин/пароль. Оба образа опубликованы в Docker Hub
(`cromovsky/yandex-disk-copy` и `cromovsky/yandex-disk-copy-caddy`) — локальная
сборка не нужна.

1. Создай конфиг из шаблона и сгенерируй хеш пароля:
   ```bash
   cp .env.example .env
   # sed удваивает $ → $$, иначе docker compose съест часть хеша
   docker run --rm caddy:2-alpine caddy hash-password --plaintext 'ВАШ_ПАРОЛЬ' | sed 's/\$/\$\$/g'
   ```
   Вставь полученную строку в `.env` в `BASIC_AUTH_HASH` (символы `$$` оставь как
   есть), задай `BASIC_AUTH_USER` и `SITE_ADDRESS` (`localhost` для проверки или
   публичный домен).

2. Подними:
   ```bash
   docker compose -f docker-compose.caddy.yml pull
   docker compose -f docker-compose.caddy.yml up -d
   ```

- `SITE_ADDRESS=localhost` — Caddy выдаёт self-signed сертификат своим
  внутренним CA (браузер предупредит — для локальной проверки нормально),
  сервис на <https://localhost>.
- `SITE_ADDRESS=disk.example.com` — публичный домен должен резолвиться на этот
  сервер, а порты 80/443 быть доступны снаружи; Caddy сам получит и продлевает
  сертификат Let's Encrypt. Сертификаты хранятся в volume `caddy_data`.

Не запускай `docker-compose.yml` и `docker-compose.caddy.yml` одновременно —
конфликт имени контейнера `yandex-disk-copy`.
