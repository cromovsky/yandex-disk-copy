<h2 id="onprem-guide">SaaS → On-premises: инструкция миграции</h2>

Этот режим находится в разработке. По умолчанию `ONPREM_ENABLED=0`:
вкладка видна, но серая и недоступна. Инструкция предназначена для разработчиков
локального стенда, которые явно включили режим по разделу 12.

Отдельная вкладка **«SaaS → On-premises»** копирует один файл или дерево каталогов
с личного Диска активного SaaS-сотрудника в личный Диск пользователя вашей
on-premises-инсталляции. Исходные файлы остаются на месте. Утилита не публикует
их, не разблокирует источник и не перезаписывает конфликтующие файлы.

**Это пилотный режим, не официальное средство миграции Яндекса.** Совместимость
с конкретной установкой, загрузку по ссылке и поведение финального перемещения
при одновременной записи ещё нужно подтвердить на стенде. Начните с небольшой
тестовой папки и отдельного тестового получателя. До проверки не используйте
режим для рабочих данных. Документация ниже описывает реализацию утилиты,
а ссылки ведут в официальную справку API и администрирования.

### 1. Что подготовить перед переносом

- Согласуйте доступ к Диску сотрудника, уведомления и необходимые согласия
  по правилам организации и [сервисных приложений Яндекс 360](https://yandex.ru/support/yandex-360/business/admin/ru/security-service-applications).
- Убедитесь, что исходный SaaS-сотрудник активен и его Диск доступен.
  Новый режим не требует административного токена API 360 и не снимает блокировки.
- Подготовьте сервисное приложение в **организации источника**: Client ID,
  Client secret и право чтения Диска. Получение описано в разделе 2.
- Создайте или выберите получателя в on-premises. Убедитесь, что он может войти
  в свой личный Диск, и получите его OAuth-токен по разделу 3.
- Попросите администратора установки сообщить адрес Disk API, адрес Passport,
  `APIGW360_CLIENT_ID`, квоту получателя и, если нужен, сертификат корпоративного CA.
- Выберите отдельную папку назначения. На время переноса исключите изменения
  выбранных исходных файлов и одновременную запись в итоговые пути назначения.
- Проверьте сетевую доступность и свободное место по разделу 4.

Общие Диски, пакетный перенос нескольких сотрудников, права доступа, версии,
публичные ссылки и исходные серверные даты в этом режиме не переносятся.
Для каждого сотрудника создавайте отдельное задание. Это копирование содержимого,
а не полная миграция всех свойств Диска.

### 2. Откуда взять доступы SaaS-источника

**ID организации.** Откройте [кабинет администратора](https://admin.yandex.ru/),
выберите организацию источника, затем **«Общие настройки» → «Профиль организации»**.
ID указан под названием организации. Это идентификатор SaaS-организации;
ID on-premises здесь не нужен. Такой путь к ID приведён и в
[официальной справке администрирования](https://yandex.ru/support/yandex-360/business/admin/ru/mail/blocklist).

**Email сотрудника.** В разделе **«Сотрудники»** откройте карточку источника
и возьмите его адрес в выбранной организации. Вводите email, не числовой UID
и не адрес администратора. См. [управление сотрудниками](https://yandex.ru/support/yandex-360/business/admin/ru/users).

**Client ID и Client secret.** Это пара реквизитов одного рабочего
OAuth-приложения, зарегистрированного как сервисное в организации источника.
Если подходящее приложение уже есть, откройте его в
[списке OAuth-приложений](https://oauth.yandex.ru/) и проверьте регистрацию
и права. Не берите ID от одного приложения, а секрет от другого.

Если приложения ещё нет:

1. Откройте [создание OAuth-приложения](https://oauth.yandex.ru/client/new/).
   По [актуальной инструкции Яндекс ID](https://yandex.ru/dev/id/doc/ru/register-api)
   выберите тип **«Для доступа к API или отладки»**.
   В старом интерфейсе может быть настройка **«Веб-сервисы»** с URL для отладки;
   ориентируйтесь на текущую официальную инструкцию, а не на старые снимки экрана.
2. Назовите приложение, например `Disk Migration Source`, и добавьте
   **`cloud_api:disk.read`**. Это минимальное право для нового режима: он читает
   метаданные и получает ссылки на скачивание. `cloud_api:disk.write`,
   `cloud_api:disk.info` и права каталога сотрудников для источника здесь не нужны.
   Уже зарегистрированное приложение с более широкими правами можно использовать,
   но расширять права специально для нового режима не требуется.
3. Сохраните приложение. На его странице скопируйте **Client ID** и
   **Client secret** в защищённое хранилище организации.
4. Зарегистрируйте приложение как сервисное по следующему порядку.

**Регистрация в организации.** Создание OAuth-приложения само по себе
не разрешает доступ к Дискам сотрудников. Функция сервисных приложений должна
быть доступна организации; проверьте требования к тарифу, почтовому домену,
роли владельца, уведомлению и согласию пользователей в
[официальной инструкции](https://yandex.ru/support/yandex-360/business/admin/ru/security-service-applications).

Для настройки используется отдельное **управляющее приложение** с правами
`ya360_security:service_applications_read` и
`ya360_security:service_applications_write`. Владелец организации получает
его пользовательский OAuth-токен: создайте управляющее приложение в
[Яндекс OAuth](https://oauth.yandex.ru/client/new/) с этими двумя правами,
сохраните и откройте ссылку с его Client ID:

```text
https://oauth.yandex.ru/authorize?response_type=token&client_id=<Client_ID_управляющего_приложения>
```

Авторизуйтесь под владельцем SaaS-организации и получите токен согласно
[инструкции сервисных приложений](https://yandex.ru/support/yandex-360/business/admin/ru/security-service-applications).
**Этот управляющий токен не вводится в форму миграции.** Рабочее приложение
источника и управляющее приложение выполняют разные задачи.

**Важно: POST заменяет весь список, а не добавляет одну запись.** Отправка
только нового приложения отключит регистрации остальных. До изменения
прочитайте [семантику замены списка](https://yandex.ru/dev/api360/doc/ru/ref/ServiceApplicationsService/ServiceApplicationsService_Create).

1. Если функция ещё не активирована, выполните её активацию согласно
   [инструкции сервисных приложений](https://yandex.ru/support/yandex-360/business/admin/ru/security-service-applications):
   `POST https://api360.yandex.net/security/v1/org/<org_id>/service_applications/activate`.
2. Получите **текущий список**:
   `GET https://api360.yandex.net/security/v1/org/<org_id>/service_applications`.
   В заголовке используйте `Authorization: OAuth <управляющий_токен>`.
   См. [описание GET](https://yandex.ru/dev/api360/doc/ru/ref/ServiceApplicationsService/ServiceApplicationsService_Get).
3. Сохраните текущие записи и добавьте рабочее приложение в массив `applications`.
   Пример **только новой записи**, не всего тела запроса:

```json
{"id": "<Client_ID_рабочего_приложения>", "scopes": ["cloud_api:disk.read"]}
```

4. Отправьте **полный список** в
   `POST https://api360.yandex.net/security/v1/org/<org_id>/service_applications`
   с `Content-Type: application/json` и тем же заголовком авторизации.
   Тело имеет вид `{"applications": [все прежние записи, новая запись]}`;
   это схема, её нужно заполнить корректными JSON-объектами.
5. Повторите GET. Убедитесь, что рабочее приложение присутствует с
   `cloud_api:disk.read`, а все прежние записи и их права сохранены.

Если рабочее приложение уже зарегистрировано, сохраните его необходимые
текущие права при изменении списка.

В утилиту вводятся Client ID и Client secret **рабочего** приложения.
Обмен этих реквизитов на краткоживущий токен сотрудника выполняется автоматически.
Отдельно получать и вводить SaaS `access_token` не нужно. Справка о правах Диска:
[SaaS Disk API: quickstart](https://yandex.com/dev/disk-api/doc/en/concepts/quickstart).

### 3. Откуда взять настройки и токен on-premises

**Адрес API.** Попросите администратора вашей установки дать HTTPS-адрес
Disk API, например `https://disk-api.onprem.example.org` или
`https://disk-api.onprem.example.org/v1/disk`. В поле **«Адрес API»** не подходят
URL веб-интерфейса Диска, адрес Passport, ссылка на документацию, путь
`/resources/upload`, параметры запроса или URL с токеном.
Домен сервисов установки может отличаться от почтового домена пользователей.
Примеры доменов в документации не определяют адрес вашей установки.

**Пользовательский OAuth-токен получателя.** Получите токен именно того
on-premises-пользователя, в чей личный Диск нужно записывать файлы:

1. Попросите администратора сообщить адрес **Passport вашей установки**
   и **`APIGW360_CLIENT_ID`**, полученный после её инициализации.
   Это Client ID для получения токена on-premises; в форму миграции он не вводится.
2. Откройте ссылку, подставив реальный домен Passport и Client ID:

```text
https://passport.onprem.example.org/oauth/authorize?response_type=token&client_id=<APIGW360_CLIENT_ID>
```

3. Войдите **под учётной записью получателя**, не под администратором
   и не под SaaS-источником. Проверьте текущую сессию перед авторизацией.
4. По [инструкции OAuth для Disk API](https://help.solution.korobka360.ru/disk/api/concepts/quickstart.html#oauth)
   скопируйте токен из адресной строки после авторизации. Если в ней есть
   `access_token=...`, возьмите только значение параметра, без остальной ссылки,
   `access_token=` и префикса `OAuth`.
5. В поле **«Владелец токена назначения»** укажите логин или email этой
   on-premises-учётной записи. После самостоятельной проверки владельца
   отметьте подтверждение под формой.

**Где администратору взять `APIGW360_CLIENT_ID`.** В Argo Workflows откройте
workflow `post-install-main-template`, затем `init-passport(0)` →
`INPUTS/OUTPUTS` → `Outputs` → `main-logs`. Найдите `APIGW360_CLIENT_ID`.
См. [постинициализацию и реквизиты OAuth](https://help.solution.korobka360.ru/devops/deployment/after-install/create-organization.html#get-data-token).
Передавайте только нужный Client ID: полный журнал содержит другие секреты
и пароли, отправлять его оператору миграции не следует.

**SCIM-токен не подходит для Диска.** Не используйте вместо пользовательского
токена SCIM-токен, управляющий SaaS-токен или Client secret.
Если пользовательский токен утрачен, пройдите авторизацию заново.

Утилита сверяет указанного владельца с `user.login`/`user.email`, если API
возвращает эти поля. Если полей нет, режим полагается на ваше явное подтверждение;
независимой проверки владельца в этом случае нет. Одно заполнение поля
«Владелец токена назначения» не превращает токен администратора в токен сотрудника.
Обзор API установки: [REST API Диска](https://help.solution.korobka360.ru/disk/api/index.html).

### 4. Как выбрать способ переноса

| Способ | Кто передаёт содержимое | Когда выбирать |
|---|---|---|
| **Напрямую по ссылке**, по умолчанию | Утилита получает временную ссылку SaaS на скачивание и передаёт её Disk API; файл скачивает on-premises | Установка может обращаться к SaaS-адресам скачивания; начните с этого способа |
| **С временным сохранением** | Сервер утилиты скачивает файл во временное хранилище, проверяет его, затем загружает в on-premises | Установка не может скачивать из SaaS, но сервер утилиты доступен обоим сервисам |

Временная ссылка на скачивание не является публикацией файла. Она даёт доступ
к содержимому: не отправляйте её в переписку или журнал диагностики.
Описание серверной загрузки по URL:
[загрузка из интернета](https://help.solution.korobka360.ru/disk/api/reference/upload-ext.html).
Описание загрузки байтов:
[загрузка файла](https://help.solution.korobka360.ru/disk/api/reference/upload.html).

**Сеть.** В обоих случаях сервер утилиты должен обращаться к OAuth/API SaaS
и к API установки. Для прямого способа **сама установка** должна иметь доступ
к адресам скачивания SaaS. Для временного сохранения к этим адресам обращается
сервер утилиты; также ему нужны адреса загрузки, возвращаемые on-premises API.
Проверки только из браузера оператора недостаточно.

**Место.** Получателю нужна квота для итоговых файлов и технических попыток.
При подготовке плана утилита ориентируется на сумму размеров файлов плюс размер
самого большого файла. Если API не сообщает квоту, предупреждение не подтверждает,
что места хватит: проверьте её с администратором.
После окончательной остановки принятые сервером загрузки могут ещё занимать
место и использовать сеть. Повторный перенос создаёт другой технический каталог,
поэтому учитывайте остатки и продолжающиеся загрузки старого задания отдельно.

В способе с временным сохранением дополнительно нужно место **на сервере
утилиты**, не на компьютере с браузером. В контейнере используется постоянный
том в `/var/lib/disk-copy`, а не прежний каталог `downloads`.
По умолчанию общий бюджет временных файлов равен 20 ГиБ, резерв свободного
места равен 1 ГиБ. Это настройки утилиты, не лимит размера файла в Яндекс Диске;
отдельно проверьте ограничения SaaS и вашей установки.

**Сертификаты.** Адрес назначения всегда HTTPS с проверкой TLS. Для корпоративного
CA администратор монтирует PEM-файл в контейнер и указывает его абсолютный путь
в `ONPREM_CA_BUNDLE`. Отключения проверки TLS нет. Новые клиенты не используют
прокси из переменных окружения; если сеть требует прокси, нужна отдельная
настройка клиентов, одной переменной `HTTPS_PROXY` недостаточно.

Автоматического переключения между способами нет. При подтверждённой ошибке
можно явно выбрать другой способ для повтора по разделу 8.

### 5. Поля формы: что вводить

Откройте вкладку **«SaaS → On-premises»**. Примеры ниже вымышленные;
подставьте значения своей организации и установки.

| Поле | Что вводить и где взять |
|---|---|
| **ID организации** | ID SaaS-организации источника из «Общие настройки» → «Профиль организации», раздел 2 |
| **Client ID сервисного приложения** | Client ID рабочего OAuth-приложения, зарегистрированного в этой SaaS-организации; не управляющего и не `APIGW360_CLIENT_ID` |
| **Client secret** | Секрет того же рабочего SaaS-приложения из его карточки на `oauth.yandex.ru` |
| **Email сотрудника** | Email активного SaaS-источника, например `employee@example.org`, из карточки сотрудника |
| **Исходный путь** | `/` для всего личного Диска, `/Документы` для папки или `/Документы/report.pdf` для файла; не URL и не путь общего Диска `vd:` |
| **Адрес API** | HTTPS-адрес Disk API вашей установки, например `https://disk-api.onprem.example.org/v1/disk`, раздел 3 |
| **Владелец токена назначения** | Проверенный логин или email on-premises-получателя, например `recipient@onprem.example.org` |
| **OAuth-токен получателя** | Только значение пользовательского токена из Passport on-premises; без `OAuth`, `access_token=` и полной ссылки |
| **Папка назначения** | Отдельный путь в личном Диске получателя, например `disk:/migration/employee@example.org`; это путь, не веб-ссылка |
| **Способ переноса** | «Напрямую по ссылке» либо «С временным сохранением», раздел 4 |
| **Подтверждаю привязку токена…** | Отметьте после проверки, что OAuth-токен действительно принадлежит указанному получателю; повторяйте проверку при предоставлении нового токена |
| **Ключ доступа к режиму on-premises** | Появляется, если администратор задал `ONPREM_ADMIN_TOKEN`; получите этот ключ у администратора сервера утилиты. Это не OAuth-токен и не ключ установки |

Не публикуйте снимки формы с секретами. Доступы передаются серверу утилиты
и хранятся в памяти, а не в журнале задания. После перезапуска их нужно ввести
заново. Настройки и пути задания сохраняются в истории, поэтому ограничьте
доступ к серверу и постоянному тому.

### 6. Подготовка плана и запуск

1. Заполните форму по разделу 5 и подтвердите владельца токена.
2. Нажмите **«Подготовить план»**. Утилита проверит доступы и обойдёт исходное
   дерево. На этом этапе она читает данные; файлы назначения ещё не записываются.
3. Дождитесь состояния **«План готов»**. Проверьте таблицу: **«Источник»**,
   **«Назначение»**, **«Размер»**, **«MD5»**, **«Результат»**. Перелистайте
   все страницы плана стрелками, проверьте число объектов и предупреждения.
4. Проверьте итоговые пути по примерам ниже. План не является неизменяемым
   снимком: если источник изменился, подготовьте новое задание.
   Проверка плана не выявляет заранее все конфликты существующих итоговых файлов.
5. Нажмите **«Начать перенос»**. Следите за состоянием, таблицей и
   **«Журналом задания»**. Файлы проходят через технический каталог получателя,
   проверяются по размеру и MD5, затем перемещаются в итоговый путь без перезаписи.
6. Для временного перерыва нажмите **«Пауза»**. Новые файлы не запускаются, но уже
   принятая операция не отменяется: утилита продолжает опрос и завершает текущий
   файл. Дождитесь фактической паузы; надпись «Пауза запрошена» ещё не означает
   остановку серверной операции. Для возобновления используйте **«Продолжить»**.
7. Для окончательной локальной остановки нажмите **«Остановить»** и подтвердите
   действие. Дождитесь состояния **«Остановлено»**; **«Остановка запрошена»**
   означает, что локальный обработчик ещё завершает остановку. Это не отменяет
   операции на сервере назначения. Остановленное задание нельзя продолжить;
   новый перенос готовится отдельно по разделу 8.

**«Ожидание другого задания».** Переносы используют общую очередь сервера
утилиты. Незавершённая операция, проверка результата или операция с неизвестным
исходом в неостановленном задании удерживает новые задания, даже если у них
другие папки назначения или в плане только каталоги. Интерфейс показывает причину, ID
и состояние удерживающего задания. После перезапуска основная подпись
**«Нужен повторный доступ»** сохраняется, а причина ожидания показывается
отдельно. Нажмите **«Открыть блокирующее задание»**, чтобы проверить его.
Если исход неизвестен, установите его в исходном задании по разделу 9.
У остановленного задания загрузки в его отдельный технический каталог
и создание этого каталога не удерживают очередь: поздний результат остаётся
в старом техническом каталоге, задание не переносит его в итоговый путь.
Незавершённое или неизвестное
**финальное перемещение** по-прежнему блокирует новые передачи до подтверждения
его завершения по разделу 9. Создание нового задания эту блокировку не снимает.
Пока ожидающее задание ещё не выполняет операцию, кнопка **«Пауза»**
останавливает его в локальной очереди без отмены операции другого задания.

**Как строится путь.** Для папки назначения
`disk:/migration/employee@example.org`:

| Исходный путь | Пример исходного объекта | Итоговый путь |
|---|---|---|
| `/` | `/Документы/report.pdf` | `disk:/migration/employee@example.org/Документы/report.pdf` |
| `/Документы` | `/Документы/report.pdf` | `disk:/migration/employee@example.org/Документы/report.pdf` |
| `/Документы/report.pdf` | Выбранный файл | `disk:/migration/employee@example.org/report.pdf` |

Выбранная папка сохраняется **со своим именем**, включая пустые каталоги.
Не добавляйте её имя второй раз в папку назначения, если не нужен путь
`…/Документы/Документы/…`. Для целого Диска копируется содержимое его корня.

Технический каталог имеет вид `disk:/.disk-copy-transfer-<job-id>` и показан
в блоке **«Каталог технических попыток»**. Он учитывается в квоте получателя.
Не переименовывайте и не удаляйте его, пока задание или связанные операции
не завершены. Справка по серверным операциям:
[получение статуса операции](https://help.solution.korobka360.ru/disk/api/reference/operations.html).

### 7. Как проверить результат

Состояние **«Завершено»** или **«Завершено с замечаниями»** описывает задание.
Чтобы принять перенос, проверьте результаты **каждого** объекта и нажмите
**«Скачать CSV»**. CSV отражает текущие результаты и попытки, а не полную историю
всех попыток; журнал задания содержит дополнительные события.

| Результат объекта | Что означает и что делать |
|---|---|
| **Перенесено** | Для файла: итог проверен по размеру и MD5, проверена актуальность источника. Для строки с размером «Каталог»: папка подготовлена, MD5 к каталогу не применяется и успех вложенных файлов не подтверждается |
| **Уже совпадает** | Итоговый файл уже существует, размер и MD5 совпали, источник проверен; повторная запись не требуется |
| **Конфликт** | Итоговый путь занят несовместимым объектом или файлом с другим содержимым. Он не перезаписывается; разберите конфликт и при необходимости создайте новое задание в другую папку |
| **Источник изменился** | Исходник не соответствует плану. Уточните нужную версию и подготовьте новый план; обычный повтор ошибок этот объект не переносит |
| **Проверка недоступна** | Нельзя подтвердить содержимое, например нет пригодной контрольной суммы. Это не успех; выясните причину с администратором |
| **Ошибка** | Попытка закончилась установленной ошибкой. Устраните причину и используйте повтор по разделу 8 |
| **Исход неизвестен** | Сервер мог принять операцию, но результат не установлен. Не повторяйте вслепую; действуйте по разделу 9 |

Убедитесь, что всем запланированным файлам соответствуют **«Перенесено»** или
**«Уже совпадает»**, а остальные результаты разобраны. На Диске получателя
проверьте ожидаемые пути, количество объектов и открытие нескольких файлов.
Сохраните CSV и ID задания для приёмки. Исходники утилита не удаляет;
их дальнейшая судьба определяется отдельно после приёмки.

API для проверки метаданных и квоты:
[метаданные ресурса](https://help.solution.korobka360.ru/disk/api/reference/meta.html),
[информация о Диске](https://help.solution.korobka360.ru/disk/api/reference/capacity.html).

### 8. Возобновление, повтор ошибок и новый перенос после остановки

После перезапуска сервера сохраняются задания, план и попытки. Запрошенная
пауза задания без активной или неизвестной операции завершается локально,
даже если доступы ещё не предоставлены; в интерфейсе видно «Перенос
приостановлен». Пауза не снимает блокировку неизвестной операции.
Доступы не сохраняются; задание не может продолжить работу без них.
Окончательно остановленное задание сохраняет состояние **«Остановлено»**
после перезапуска сервера; обычное возобновление к нему не применяется.

1. В **«Истории заданий»** выберите нужный ID. Стрелки показывают более старые
   и более новые страницы истории; кнопка обновления перечитывает список.
2. Настройки выбранного задания подставятся в форму. Секреты и подтверждение
   владельца будут очищены. Введите Client secret источника и OAuth-токен
   **того же получателя**, заново проверьте владельца и отметьте подтверждение.
   Если показано поле ключа доступа, введите и ключ сервера утилиты.
3. Не меняйте ID организации, Client ID, email, исходный путь, адрес API,
   владельца, папку назначения и **первоначальный способ переноса**.
   Эти параметры привязаны к заданию. Для другого источника или назначения
   создайте новое задание.
4. Нажмите **«Предоставить доступ»**, затем **«Продолжить»**.
   Для ещё не запущенного готового плана нажмите **«Начать перенос»**.
5. Если есть неизвестный исход, сначала выполните раздел 9.

**Повтор установленной ошибки.** Устраните причину, выберите способ в отдельном
поле **«Повтор ошибок»** и нажмите **«Повторить ошибки»**. Повтор запускается
этой кнопкой; можно явно выбрать **«С временным сохранением»**, если прямое
скачивание недоступно. Для предоставления доступов первоначальный способ
в основной форме менять не нужно.

Повтор охватывает только объекты с результатом **«Ошибка»**. Конфликты,
изменившиеся исходники, недоступная проверка и неизвестные исходы не повторяются
этой кнопкой. Сохранившийся локальный файл используется повторно только после
проверки содержимого и актуальности источника. Восстановления скачивания
с последнего байта нет: незавершённое скачивание начинается заново.

**Новый перенос после окончательной остановки.** Остановка сохраняет исходники,
уже полученные итоговые файлы, историю и попытки старого задания. Она не удаляет
и не перезаписывает файлы. Принятая сервером загрузка, в том числе загрузка
с неизвестным исходом, может завершиться позже только в уникальном техническом
каталоге старого задания. Старое задание больше не запускает перенос таких
файлов в итоговые пути. Неизвестный исход таких загрузок или создания старого
технического каталога не удерживает новый перенос. Учитывайте дополнительный
расход сети и квоты.

1. В истории откройте задание в состоянии **«Остановлено»**, **«Завершено»**
   или **«Завершено с замечаниями»**.
2. Введите заново Client secret источника и OAuth-токен того же получателя,
   проверьте владельца токена и отметьте подтверждение. Если требуется ключ
   доступа к режиму, введите его тоже. Первоначальные ID организации, Client ID,
   email, исходный путь, адрес API, владелец, папка назначения и способ переноса
   сохраняются: эта кнопка не предназначена для изменения параметров задания.
3. Нажмите **«Повторить перенос заново»**. Утилита создаст новое задание с новым
   ID, планом и отдельным путём технического каталога. Старое задание и его попытки
   сохранятся в истории; старый технический каталог не переиспользуется.
4. Дождитесь **«План готов»**, проверьте все страницы плана и предупреждения,
   затем вручную нажмите **«Начать перенос»**. Создание нового плана само по себе
   не запускает передачу. Итоговые файлы с совпадающими размером и MD5 будут
   пропущены как **«Уже совпадает»**; несовпадающие файлы не перезаписываются.

Если у старого задания осталось незавершённое или неизвестное финальное
перемещение, новый перенос будет ждать подтверждения его завершения. Проверка
такой операции описана в разделе 9. Остановка не отменяет это перемещение,
поэтому уже отправленная серверу операция ещё может изменить итоговый путь.
Технические каталоги очищаются только вручную и после подтверждения завершения
всех связанных серверных операций по разделу 10.

### 9. Что делать при неизвестном исходе

**Таймаут, ответ `404`, наличие или отсутствие файла сами по себе не доказывают
завершение операции.** Если ответ на импорт, загрузку или перемещение потерян,
сервер мог продолжить работу. Утилита блокирует повтор, чтобы не отправить
такую операцию ещё раз. Для неостановленного задания блокировка действует
на общую очередь, в том числе на задания с другими папками назначения.
У остановленного задания изолированные загрузки в старый технический каталог
и создание этого каталога не блокируют новый перенос; неизвестное или
незавершённое финальное перемещение блокирует его до подтверждения завершения.
Не удаляйте попытку и не снимайте блокировку вручную. Исход блокирующей операции
нужно установить в первоначальном задании через
**«Сохранить проверенный исход»** (`/resolve`) после проверки администратором.
Новое задание и смена способа переноса не разрешают неизвестный исход;
автоматический повтор такой операции не запускается.

**Если блокирующее задание остановлено.** Для известного ID финального
перемещения утилита может продолжить проверку статуса с ещё доступными токенами.
Если доступы утрачены, откройте остановленное задание, введите доступы к тому же
источнику и получателю и нажмите **«Предоставить доступ»**. Это только проверка
доступов и состояния серверной операции: задание остаётся **«Остановлено»**.
Для неизвестного финального перемещения или недоступного статуса известной
операции попросите администратора установить ID или подтвердить завершение
по журналам. В блоке **«Проверка итогового перемещения»** используйте
**«Сохранить проверенный исход»** по инструкции ниже. Форма доступна у
остановленного задания только для итоговых перемещений, которые удерживают
очередь, включая операции с известным ID. Она записывает результат,
не возобновляет перенос и не запускает старые попытки. Очередь освобождается
только после подтверждения завершения операции. Кнопки продолжения, запуска
и повтора ошибок у остановленного задания недоступны.

В блоке **«Неопределённый исход операции»** выберите **«Попытку»** и используйте
один из двух вариантов:

**Где искать серверную операцию.** Во встроенной Grafana инсталляции откройте
**Explore**, выберите источник **Loki**, задайте интервал попытки и фильтр
по техническому каталогу первоначального задания `.disk-copy-transfer-<ID>`.
Для Kubernetes адрес Grafana можно уточнить у администратора или посмотреть
в столбце `HOSTS` команды `kubectl get ingress -n monitoring`. Если там нет
Grafana, уточните её namespace и способ доступа: состав Ingress зависит от
конфигурации стенда. Адрес из примера официальной справки не является адресом
вашей установки. В Loki выберите доступные метки компонентов Диска; конкретные
имена namespace, pod и меток зависят от установки. Если поиск полного пути
пустой, попробуйте ID задания без префикса: путь мог быть закодирован в URL.
Администратору нужно сопоставить `POST /v1/disk/resources/upload` или перемещение
с фоновой задачей и установить её ID или подтверждённый конечный результат.
Каталог `disk:/...` и ID задания утилиты не являются ID серверной операции.
Если путь не записан в логах, используйте время попытки и журналы компонентов
Диска. Не передавайте полные запросы с OAuth-токенами или подписанными URL.
Порядок доступа к Grafana и просмотра логов описан в
[разделе мониторинга](https://help.solution.korobka360.ru/devops/deployment/admin/monitoring.html#work-with-logs).

**Если администратор нашёл ID серверной операции:** введите его в
**«Восстановленный ID операции»**, сохранив форму ссылки на статус:

- для `/operations/<ID>` введите только `<ID>`;
- для `/operations?id=<ID>` введите `?id=<ID>`.

Утилита сохраняет эту форму и использует соответствующий адрес при опросе.
Утилита принимает ID длиной от 1 до 256 символов: `A-Z`, `a-z`, `0-9`, `-` и `_`.
Полный URL, дополнительные параметры и фрагмент ссылки
в это поле не принимаются. Не вводите токен или ID задания утилиты.
Формы ссылок описаны в справке назначения:
[статус операции](https://help.solution.korobka360.ru/disk/api/reference/operations.html)
и [ответ на загрузку из интернета](https://help.solution.korobka360.ru/disk/api/reference/upload-ext.html).
Если `?id=` присутствует в исходной ссылке, сохраните его при вводе.
Отметьте подтверждение, нажмите
**«Сохранить проверенный исход»**. Утилита опросит операцию. В неостановленном
задании, если операция ещё выполняется или завершилась успешно, нажмите
**«Продолжить»** для дальнейшего опроса и проверок. Если уже установлена ошибка,
используйте **«Повторить ошибки»**; обычное продолжение не повторяет неудачные
файлы. Остановленное задание только фиксирует установленный исход финального
перемещения и остаётся остановленным.

**Если ID восстановить нельзя, но исход подтверждён журналами установки:**
выберите **«Результат по журналам администратора»**: **«Успешно завершена»**
или **«Завершилась ошибкой»**. Введите описание подтверждения длиной от 20 символов,
например время и внутренний номер разбора. Не включайте токены и ссылки.
Отметьте подтверждение установленного результата и отсутствия продолжающейся
операции; нажмите **«Сохранить проверенный исход»**.

В неостановленном задании после подтверждённого успеха нажмите **«Продолжить»**:
утилита всё равно проверяет содержимое, это действие не переводит файл сразу
в **«Перенесено»**. После подтверждённой ошибки используйте **«Повторить ошибки»**.
В остановленном задании подтверждение исхода не запускает дальнейшую работу;
для нового переноса выполните раздел 8.
В журнале хранится контрольный отпечаток описания подтверждения, а не его текст.
Не выбирайте терминальный результат по предположению.

Если неизвестен исход создания **самого технического корня**, это отдельная
ситуация: форма разрешения файловой попытки её не исправляет.
После **«Остановить»** эта операция может завершиться
только созданием старого уникального технического каталога и не блокирует новый
перенос по разделу 8. Старый каталог не переиспользуется и не удаляется при
повторном переносе. Для его ручной очистки администратор должен подтвердить
завершение создания каталога и всех связанных операций по разделу 10.

### 10. Очистка временных файлов

**«Очистить локальные файлы»** удаляет только принадлежащие заданию временные
файлы на сервере утилиты, для которых попытка уже завершена. Работающие,
неопределённые и посторонние объекты она не затрагивает. После успешного переноса
локальная временная копия также очищается автоматически. Кнопка не удаляет
исходники SaaS и итоговые файлы получателя.

**Технические остатки в on-premises автоматически не удаляются**, включая пустые
каталоги. Их список в блоке временных файлов относится к удалённому Диску,
а не означает, что объекты уже удалены. Администратор может очистить соответствующий
`disk:/.disk-copy-transfer-<job-id>` только после подтверждения завершения
всех связанных серверных операций и проверки итогов задания. Состояние
**«Остановлено»** подтверждает только локальную остановку и не разрешает удалять
этот каталог: принятые сервером загрузки ещё могут выполняться.

Не удаляйте постоянный том миграции ради освобождения места: в нём находится
и журнал восстановления. Ручная очистка работающего задания может лишить
утилиту данных, необходимых для установления исхода.

### 11. Частые проблемы

| Симптом | Что проверить и как продолжить |
|---|---|
| Вкладка серая и не нажимается | Режим в разработке и выключен по умолчанию (`ONPREM_ENABLED=0`). Для локального стенда включите его по разделу 12. Он не зависит от `CROSS_ORG_ENABLED` |
| Запрос требует HTTPS или ключ доступа | Проверьте способ размещения и `ONPREM_ADMIN_TOKEN`, раздел 12. Ключ выдаёт администратор сервера утилиты |
| SaaS token-exchange возвращает `400 invalid_request / Unauthorized` | Проверьте организацию, активность пользователя, регистрацию рабочего приложения и `cloud_api:disk.read`. GET списка после исправления должен подтверждать регистрацию |
| Отказ авторизации источника | Сверьте Client ID и Client secret одного рабочего приложения; управляющее приложение для миграции не подходит |
| API назначения возвращает `401`/`403` | Проверьте реальный адрес API, токен именно из Passport установки и его владельца. При необходимости получите новый пользовательский токен и предоставьте доступ заданию |
| Владелец токена не совпадает | Проверьте учётную запись, под которой получен токен. Для существующего задания нельзя подставлять другого получателя |
| Ошибка сертификата | Проверьте имя сервера, цепочку сертификатов и `ONPREM_CA_BUNDLE` с администратором. Не отключайте проверку TLS |
| Прямой способ завершился ошибкой скачивания | Проверьте доступ из установки к SaaS-адресам скачивания. Только после установленной ошибки выберите временное сохранение для повтора; при неизвестном исходе сначала раздел 9 |
| Не хватает квоты назначения | Учтите итоговые файлы и технический каталог. Освободите или увеличьте квоту после проверки завершения операций; предупреждение о недоступной квоте не означает достаточное место |
| Не хватает места для временного сохранения | Проверьте свободное место сервера утилиты, общий бюджет и резерв. Очистите только завершённые локальные попытки или увеличьте бюджет; настройки приведены ниже |
| После перезапуска перенос не идёт | Для неостановленного задания заново предоставьте доступы, затем продолжите. Для «Остановлено» подготовьте новый перенос по разделу 8; журнал и введённые токены имеют разный срок хранения |
| «Повторить ошибки» не исправляет конфликт или неизвестный исход | Это ожидаемое ограничение. Для конфликта разберите итоговый путь; для неизвестного исхода следуйте разделу 9 |
| Проверенных байтов меньше объёма плана | Просмотрите все страницы результатов и CSV: в счётчик не должны приниматься непроверенные файлы. Не считайте завершение задания подтверждением каждого файла |

### 12. Размещение, хранение и настройки администратора

**Локальный стенд разработки.** В коде, Dockerfile и обоих базовых Compose-файлах
`ONPREM_ENABLED=0` и `ONPREM_ALLOW_INSECURE_HTTP=0`. Для тестирования из каталога
репозитория добавьте `docker-compose.dev.yml`:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build -d
```

Файл с настройками разработки явно включает оба флага со значением `1`.
Он использует то же имя контейнера и существующий том `migration-data`.
При пересоздании контейнера журнал сохраняется, а доступы к заданиям нужно
предоставить заново. Открывайте `http://localhost:8000` или
`http://127.0.0.1:8000`.
Без ключа разрешены localhost и literal loopback, в том числе при адресе клиента
из Docker bridge; проверка Origin сохраняется. Если задан `ONPREM_ADMIN_TOKEN`,
он обязателен даже с этим флагом. Обычный контейнер не обслуживает TLS:
`https://localhost:8000` для него не подходит.

**При HTTP токены между браузером и утилитой не шифруются.** Такой вариант
предназначен для локального тестирования. Он не меняет требование HTTPS к API
назначения.
**Тестовый сервер должен быть изолирован от посторонних клиентов.** Текущий
Compose публикует порт 8000 на всех интерфейсах. Открытие `localhost` в браузере
не ограничивает доступ к этому порту; проверки имени и Origin не заменяют
сетевую защиту. Используйте изолированную сеть или firewall, либо привяжите
порт в Compose только к loopback: `127.0.0.1:8000:8000` вместо `8000:8000`.
Для стенда с HTTPS используйте вариант с Caddy без `docker-compose.dev.yml`;
разрешение HTTP останется выключенным.

**Стенд разработки с HTTPS.** Нужны HTTPS, ограничение доступа и отдельный длинный
случайный `ONPREM_ADMIN_TOKEN` в защищённой конфигурации запуска. Тот же ключ
оператор вводит в поле доступа. Вариант с Caddy сохраняет существующую basic-auth
и проверяет ключ в приложении. Предварительно настройте домен, HTTPS/basic-auth
и ключ по общей инструкции размещения. Для явного включения режима и сборки
изменённых исходников:

```bash
ONPREM_ENABLED=1 docker compose -f docker-compose.caddy.yml up --build -d
```

Не запускайте одновременно обычный Compose и вариант с Caddy: у них одинаковое
имя контейнера. В варианте с Caddy не публикуйте порт приложения наружу:
приложение доверяет proxy-заголовкам в закрытой сети этих двух сервисов.
В обычном запуске готовых образов режим выключен; включение для стенда
разработки требует отдельной настройки `ONPREM_ENABLED=1`.

**Постоянное хранилище.** SQLite-журнал и временные файлы находятся в
`ONPREM_DATA_DIR`: без Docker по умолчанию `./migration-data`, в контейнере
`/var/lib/disk-copy`, постоянный том `migration-data`. Резервируйте хранилище
и не удаляйте том при пересоздании контейнера. Пути и email в журнале требуют
ограничения доступа. Для одного тома используйте один процесс приложения
и один экземпляр; второй worker отклоняется блокировкой. NFS и несколько
Uvicorn workers не поддерживаются.

| Переменная | Значение по умолчанию и назначение |
|---|---|
| `ONPREM_ENABLED` | `0`; значение `1` явно включает режим в разработке |
| `ONPREM_ADMIN_TOKEN` | Не задан. Ключ режима для защищённого размещения; не OAuth-токен |
| `ONPREM_ALLOW_INSECURE_HTTP` | `0`; значение `1` разрешает временный HTTP-тест. В `docker-compose.dev.yml` задано `1` |
| `ONPREM_DATA_DIR` | `./migration-data` без Docker, `/var/lib/disk-copy` в контейнере; журнал и временные файлы |
| `ONPREM_STAGING_MAX_BYTES` | `21474836480`, общий бюджет временных файлов 20 ГиБ |
| `ONPREM_STAGING_RESERVE_BYTES` | `1073741824`, резерв свободного места 1 ГиБ |
| `ONPREM_API_READ_RPS` | `10`, темп чтения API установки |
| `ONPREM_API_WRITE_RPS` | `2`, темп изменения API установки |
| `ONPREM_CA_BUNDLE` | Системные доверенные CA; при корпоративном CA задайте абсолютный путь к смонтированному PEM-файлу |

Темп on-premises является настройкой утилиты, а не заявленным лимитом продукта.
SaaS использует общий бюджет запросов с другими режимами утилиты.
Автоматическая смена способа, массовый административный доступ к on-premises,
общие Диски и восстановление по диапазонам байтов в эту версию не входят.
