<h2 id="onprem-guide">SaaS → On-premises: краткая инструкция</h2>

Режим копирует личные и общие SaaS-диски **в корень существующего общего Диска On-premises**: личный — в папку с email, общий — в папку «название (ID)». Можно выбрать один личный источник или загрузить список дисков. Исходники остаются на месте; права, версии и исходные серверные даты не переносятся.

Режим доступен в обоих публичных образах релиза **3.3.0**. Файлы передаются с временным кешем на машине утилиты. Для доступа к интерфейсу нужны локальный HTTP с разрешением в настройках либо HTTPS и ключ режима — см. [настройку](#onprem-admin).

**Перед запуском:** личный источник публикуется для скачивания; ссылки остаются открытыми после переноса и остановки. Общие SaaS-диски скачиваются под токеном сотрудника с доступом, только с временным кешем.

### Быстрый запуск

1. Подготовьте [доступы SaaS](#onprem-source-access) и [общий Диск On-premises](#onprem-destination-access). Источник должен быть активным пользователем; утилита его не разблокирует.
2. Заполните форму и подтвердите владельца токена назначения.
3. Нажмите **«Dry Run»**. Дождитесь **«План готов»**, проверьте итоговые пути, объём и предупреждения. Это проверка без публикации источника и записи файлов назначения.
4. В плане снимите галочки с ненужных файлов и папок, затем нажмите **«Начать перенос»**. Все объекты выбраны по умолчанию. Для изменения выбора новый Dry Run не нужен; при изменении источника, назначения или параметров плана выполните его заново.
5. Проверьте результаты всех файлов и сохраните **«Скачать отчёт CSV»**. Для разбора ошибок есть отдельная кнопка **«Скачать журнал CSV»**.

В заголовке **«Задание от …»** и истории указаны дата и время создания задания при Dry Run, в часовом поясе браузера. В истории рядом показаны email источника и состояние. Пауза и продолжение не меняют эту дату; **«Начать заново»** создаёт отдельное задание с новой датой.

На время переноса исключите изменения выбранных исходников и одновременную запись в итоговые пути. План не является снимком Диска.

### Выбор файлов и папок

В одиночном задании и CSV-списке после полного Dry Run все объекты отмечены.
Галочка папки меняет выбор всего её содержимого, включая другие страницы плана.
Выбор вложенного файла включает нужные родительские папки. Исключённые объекты
не попадают в очередь, не считаются ошибками и не повторяются.
Выбор сохраняется после обновления страницы и перезапуска контейнера.
Менять его можно до первого запуска, без нового Dry Run. Для другого состава
после начала переноса создайте новый план. Если ничего не выбрано, запуск
недоступен. В списке источник без выбранных объектов пропускается.
Конфликтующий файл можно исключить, чтобы перенести остальные.

### Перенос по списку

В одном CSV — до **1000 строк с дисками**, без учёта заголовка.
Личные и общие диски можно смешивать. Если строк больше, разделите список
на несколько CSV.

1. В **«Источники»** выберите **«Список дисков из CSV»** и загрузите шаблон:

   ```csv
   type,email,vd_hash,path
   personal,employee@example.org,,/
   shared,reader@example.org,shared-disk-id,/
   ```

   Для общего диска email — сотрудник с доступом, `vd_hash` — метка из `/vd/`.
   Для личного — email владельца, `vd_hash` пустой. Настройки сервисного
   приложения и общего диска On-premises одинаковы для всего списка.
2. **Dry Run** проверяет доступ, затем полностью обходит каждый источник и
   сравнивает назначение. Публикации, скачивания и создания папок нет.
   Совпадение — только по размеру и MD5; другое содержимое — конфликт.
3. Проверьте пути, объём к переносу и ошибки. У проблемного источника снимите
   галочку либо нажмите **«Повторить Dry Run»** после исправления причины.
   Запуск доступен только с полными планами всех выбранных источников.
4. Откройте **«Файлы»** и снимите галочки с объектов, которые не нужно переносить.
   Затем нажмите **«Начать перенос»**. Максимум четыре источника работают одновременно
   во всей утилите, по одному файлу на источник. **«Файлы»** открывает план,
   **«Подробный журнал»** — подробности и точечные повторы файла.

Папка общего источника — `/<название> (<ID>)`, имя фиксируется при первом
Dry Run. План фиксирует состав: новые файлы требуют нового Dry Run, изменённые
исходники перепроверяются перед передачей. Проверка без записи не гарантирует,
что позднее публикация или загрузка будут разрешены сервером.

Пауза, продолжение и полная остановка действуют на весь список. Ошибка одного
источника не мешает проверке остальных. При включённых автоматических повторах
недоступность On-premises останавливает загрузки в эту установку, временные файлы
остаются в кеше. Без автоматических повторов ошибка файла не останавливает очередь.
После перезапуска выберите список в истории и введите Client secret, токен
назначения и, если использовали, ADMIN_TOKEN заново. План и журнал сохраняются,
секреты — нет.
Подтвердите владельца токена назначения и нажмите **«Продолжить»** для
восстановления доступа и продолжения прерванной работы. Если план готов, но ещё
не запускался, затем нажмите **«Начать перенос»**.
CSV плана и журнала содержат источник каждой строки.

Если остановили Dry Run, **Dry Run** и **«Начать заново»** создадут новую проверку.
Прежний обход и повторы запросов прекращаются, история сохраняется.
Уже отправленный HTTP-запрос может завершаться до сетевого тайм-аута;
новая проверка ждёт свободного слота, сохраняя общий лимит четырёх источников.

<a id="onprem-source-access"></a>
### Доступы SaaS: что и где взять

| Поле формы | Что вводить |
|---|---|
| **ID организации (ORGID)** | ID организации источника: [кабинет администратора](https://admin.yandex.ru/) → «Общие настройки» → «Профиль организации», под названием |
| **Client ID сервисного приложения** | Client ID рабочего приложения из его карточки на [Яндекс OAuth](https://oauth.yandex.ru/). Оно должно быть зарегистрировано как сервисное в организации источника |
| **Client secret** | Секрет того же рабочего приложения. ID и секрет разных приложений не подходят |
| **Токен администратора (ADMIN_TOKEN, необязательно)** | OAuth-токен администратора SaaS с правом `directory:read_users`: дополнительно проверяет email в указанной организации и блокировку сотрудника. Как получить — [шаг 4 инструкции](https://github.com/cromovsky/yandex-disk-copy/blob/v3.3.0/docs/INSTRUCTION.md#шаг-4-получить-admin_token) |
| **Email владельца личного Диска SaaS** | Email активного сотрудника из раздела «Сотрудники». Не UID, не ID диска и не адрес администратора |
| **Исходный путь** | `/` — весь личный Диск; `/Документы` — папка; `/Документы/report.pdf` — файл. Не веб-ссылка |

Токен сотрудника утилита получает и обновляет автоматически по Client ID,
Client secret и email. ORGID и ADMIN_TOKEN в запрос выдачи OAuth-токена не входят.
ORGID обязателен в форме; ADMIN_TOKEN автоматически не обновляется.
Если ADMIN_TOKEN указан, перед выдачей **и обновлением** токена проверяются
принадлежность сотрудника организации ORGID и его активность. Без ADMIN_TOKEN
остаётся доступ через сервисное приложение; заблокированного сотрудника нужно
разблокировать в админке и повторить Dry Run. Статус утилита не меняет.

Для общего Диска назначения нужен отдельный **токен сотрудника On-premises**.
SaaS ADMIN_TOKEN не заменяет ни Client secret источника, ни токен назначения.
После перезапуска секрет и использованные токены вводятся заново; план и журнал
сохраняются.

**Если рабочего сервисного приложения ещё нет:**

1. [Создайте OAuth-приложение](https://oauth.yandex.ru/client/new/) типа **«Для доступа к API или отладки»** по [инструкции Яндекс ID](https://yandex.ru/dev/id/doc/ru/register-api).
2. Добавьте `cloud_api:disk.read` и `cloud_api:disk.write`. Чтение нужно для файлов, запись — для обязательной [публикации](https://yandex.ru/dev/disk-api/doc/ru/reference/publish) источника.
3. Сохраните **Client ID** и **Client secret**. Затем зарегистрируйте приложение как сервисное — одного создания в OAuth недостаточно.

**Регистрация: отдельное управляющее приложение, один раз для организации.** Выполняет владелец организации. Доступность функции, требования к домену, уведомлению и согласию сотрудников проверьте в [инструкции сервисных приложений](https://yandex.ru/support/yandex-360/business/admin/ru/security-service-applications).

**POST заменяет весь список сервисных приложений.** Отправка только нового приложения отключит остальные регистрации. [GET списка](https://yandex.ru/dev/api360/doc/ru/ref/ServiceApplicationsService/ServiceApplicationsService_Get) · [POST полного списка](https://yandex.ru/dev/api360/doc/ru/ref/ServiceApplicationsService/ServiceApplicationsService_Create).

1. Создайте второе OAuth-приложение с правами `ya360_security:service_applications_read` и `ya360_security:service_applications_write`.
2. Под владельцем SaaS-организации получите его токен по ссылке, подставив Client ID **управляющего** приложения:

```text
https://oauth.yandex.ru/authorize?response_type=token&client_id=<Client_ID_управляющего_приложения>
```

3. Если функция ещё не активирована, выполните `POST https://api360.yandex.net/security/v1/org/<org_id>/service_applications/activate`.
4. Получите текущий список: `GET https://api360.yandex.net/security/v1/org/<org_id>/service_applications`.
5. Добавьте рабочее приложение, **сохранив все прежние записи и их права**, и отправьте полный список через POST на тот же адрес. Во всех запросах используйте `Authorization: OAuth <управляющий_токен>`, для POST списка — `Content-Type: application/json`.
6. Повторите GET: рабочее приложение должно присутствовать с нужными правами, прежние регистрации должны сохраниться.

Пример **только добавляемой записи**, не полного тела запроса:

```json
{"id": "<Client_ID_рабочего_приложения>", "scopes": ["cloud_api:disk.read", "cloud_api:disk.write"]}
```

Полное тело имеет поле `applications` с массивом всех записей. Управляющий токен нужен только для регистрации; в форму переноса вводятся ID и секрет **рабочего** приложения.

<a id="onprem-destination-access"></a>
### Доступы On-premises: что и где взять

| Поле формы | Что вводить |
|---|---|
| **Адрес API** | HTTPS-адрес **Disk API вашей установки**, который даст администратор, например `https://disk-api.onprem.example.org/v1/disk`. Не адрес веб-Диска, Passport или документации |
| **Владелец токена назначения** | Логин или email on-premises-учётной записи, под которой получен токен |
| **Токен сотрудника с доступом к общему диску** | Пользовательский OAuth-токен из Passport вашей установки; нужны права чтения и записи Диска и доступ `read`/`write` к выбранному общему Диску |
| **Метка существующего общего диска** | `vd_hash`: часть после `/vd/` в веб-адресе общего Диска. Также доступна через [информацию об общем Диске](https://help.y360-dr.korobka360.ru/disk/api/reference/shared-disks/shd-info.html). Не `resource_id`, UUID или email |
| **Ключ доступа к режиму on-premises** | Если поле показано, получите ключ `ONPREM_ADMIN_TOKEN` у администратора **утилиты**. Это не OAuth-токен |

Адреса и email в примерах вымышленные. Используйте настройки своей установки.

**Как получить токен назначения:**

1. Попросите администратора сообщить адрес **Passport** и `APIGW360_CLIENT_ID` установки. Этот Client ID нужен только для получения токена, в форму переноса он не вводится.
2. Откройте ссылку и войдите под оператором, у которого есть доступ к общему Диску:

```text
https://passport.onprem.example.org/oauth/authorize?response_type=token&client_id=<APIGW360_CLIENT_ID>
```

3. По [инструкции OAuth](https://help.solution.korobka360.ru/disk/api/concepts/quickstart.html#oauth) скопируйте **значение `access_token`** из адресной строки. Вставляйте без `OAuth`, без `access_token=` и без остальной ссылки.
4. Укажите владельца этого токена и отметьте подтверждение под формой. Один оператор может переносить данные разных SaaS-сотрудников на общий Диск.

**SCIM-токен, Client secret и управляющий SaaS-токен для назначения не подходят.** Утилита сверяет владельца, если API возвращает `user.login` или `user.email`; иначе опирается на ваше подтверждение.

Администратору: `APIGW360_CLIENT_ID` находится в Argo Workflows → `post-install-main-template` → `init-passport(0)` → `INPUTS/OUTPUTS` → `Outputs` → `main-logs`. Передайте оператору только Client ID: полный журнал содержит другие секреты. [Официальная инструкция](https://help.solution.korobka360.ru/devops/deployment/after-install/create-organization.html#get-data-token).

### Временный кеш, публикация и итоговый путь

**С временным сохранением в кэш:** утилита скачивает файл на свою машину, проверяет размер и MD5, загружает в On-premises и проверяет результат. Машине утилиты нужны доступ к обоим сервисам и свободное место.

После успешного переноса файла утилита ждёт **20 секунд** перед следующей
передачей того же источника, в том числе в CSV. Если автоматические повторы
отключены, после пропуска файла из-за ошибки она также ждёт 20 секунд перед
следующим файлом или папкой. Причина, сторона сбоя и полученные HTTP-код и код
API остаются в журнале. При включённых повторах задержки между попытками
сохраняются. Очередь продолжается автоматически; параллельные источники ждут
независимо. Создание папок, исключённые пользователем объекты и уже совпадающие
файлы новую паузу не запускают; после последнего объекта ожидания нет. Во время
ожидания доступны **«Пауза»** и **«Остановить полностью»**, проверка уже принятых
сервером операций продолжается.

Новые задания загружают файлы **сразу под исходными именами**, без служебных папок на общем Диске. Обычный перенос не перезаписывает существующие файлы; точечный повтор может заменить частичный файл своей прерванной загрузки.

**Публикация личного источника обязательна** и начинается после **«Начать перенос»**:

- Для выбранной папки публикуется сама папка; вложенные файлы скачиваются по одному, без ZIP и отдельной публикации каждого файла.
- Для выбранного файла публикуется этот файл.
- Для пути `/` публикуются папки верхнего уровня и отдельные файлы в корне.

**Ссылки остаются публичными после завершения, ошибки и остановки.** Доступ к папке распространяется и на добавленные позже файлы. Существующие пароли и ограничения ссылок сохраняются; если они мешают скачиванию, причина попадёт в журнал.

Папка сотрудника создаётся автоматически в корне общего диска; выбора другой папки в форме нет. Пример для источника `employee@example.org`:

| Исходный путь | Куда попадёт `report.pdf` |
|---|---|
| `/` с файлом `/Документы/report.pdf` | `/employee@example.org/Документы/report.pdf` |
| `/Документы` | `/employee@example.org/Документы/report.pdf` |
| `/Документы/report.pdf` | `/employee@example.org/report.pdf` |

Выбранная исходная папка сохраняется со своим именем, включая пустые каталоги.

В карточке **«Направление»** источник указан слева, получатель — справа. Пример: `employee@example.org (SaaS) → Общий диск On-premises [метка] · /employee@example.org`. После разделителя `·` показана папка получателя.

<a id="onprem-buttons"></a>
### Кнопки и повторный запуск

| Кнопка | Что делает |
|---|---|
| **Dry Run** | Проверяет доступы, общий Диск, квоту и составляет план. Не публикует и не переносит файлы; не выявляет заранее все конфликты назначения |
| **Начать перенос** | Запускает готовый план после Dry Run |
| **Пауза** | Не запускает новые передачи; текущая принятая сервером операция проверяется до завершения |
| **Продолжить** | Снимает паузу и обрабатывает оставшиеся файлы плана. После завершения очереди повторяет обычные ошибки; прерванную передачу повторяйте кнопкой у файла |
| **Остановить полностью** | Отменяет незавершённые действия **в утилите**, прекращает фоновые проверки и освобождает очередь и пути. Дождитесь «Остановлено полностью»; доступы к дискам для остановки не нужны |
| **Начать заново** | Создаёт новый план для того же источника и общего диска. После «План готов» нужно снова нажать «Начать перенос»: только тогда создаётся папка назначения и публикуется личный источник |
| **Проверить и повторить** | Кнопка в строке файла: проверяет общий Диск и повторяет загрузку из кеша. Подробнее [ниже](#onprem-retry) |
| **Очистить локальный кеш** | Общая кнопка внизу режима. Удаляет все скачанные временные файлы всех заданий, включая остановленные и незавершённые. Выбирать задание и вводить токены дисков не нужно; выполняющийся перенос сначала приостановите или остановите |

**Полная остановка не отменяет принятую сервером операцию:** документированный API On-premises не предоставляет такую команду. Она может продолжаться и расходовать квоту и сеть. Утилита сохраняет её историю, освобождает пути и разрешает новый перенос. Остановленное задание продолжить нельзя — используйте **«Начать заново»**.

Файлы, уже совпадающие по размеру и MD5, получают **«Уже совпадает»**. Несовпадающие файлы остаются **«Конфликтом»**: полная остановка не разрешает их перезаписывать или удалять.

**После перезапуска контейнера:** выберите задание в истории, введите Client secret и токен назначения заново, подтвердите владельца. При необходимости введите ключ режима. Затем нажмите **«Продолжить»**, **«Начать перенос»** для готового плана или **«Начать заново»** для остановленного задания. Доступ проверяется автоматически; отдельной кнопки предоставления доступа нет. Параметры выбранного задания менять нельзя — для другого источника или назначения нужен новый план.

При обновлении старого локального стенда см. [примечание о тестовых заданиях](https://github.com/cromovsky/yandex-disk-copy/blob/v3.3.0/docs/UPDATE.md#old-local-jobs). Их история и выгрузки сохраняются.

Секреты хранятся только в памяти. В истории остаются параметры, пути, попытки и журнал; не публикуйте заполненную форму и ограничьте доступ к хранилищу утилиты.

### Повторы и проверка результата

Галочка **«Автоматически повторять при ошибках»** по умолчанию включена.
Её можно менять перед запуском и во время работы, в том числе для всего
списка дисков; новый Dry Run не нужен. Без галочки выполняется одна попытка:
при ошибке файл пропускается, обработка остальных продолжается. В журнале —
путь, этап, сторона сбоя (SaaS, On-premises или локальный кеш), причина,
HTTP-статус и код API, если сервер их вернул. Ожидающий повтор отменяется;
уже отправленный запрос завершается или дожидается тайм-аута.
Ошибки подготовки доступа и обхода источника показываются отдельно.

Кнопка **«Проверить и повторить»** остаётся доступна: без автоматических
повторов одно нажатие запускает одну попытку. Обновление токена после HTTP 401,
пауза после HTTP 429 и проверка уже принятой сервером операции сохраняются.
При повторном включении галочки пропущенные файлы сами не запускаются.

При включённых автоматических повторах для временных сбоев получения ссылки или скачивания предусмотрено **5 попыток всего**: первая и четыре повтора через **2, 4, 8 и 16 секунд**, плюс случайная задержка до 25 %. Больший `Retry-After` сервера имеет приоритет. После пятой неудачи файл получает **«Ошибка»**, в журнале — **«Пропущен»**; обработка остальных файлов продолжается. Ошибки авторизации и нехватку места повтор не исправит.

При ошибке связи с On-premises утилита прекращает передачу или ожидание операции этого файла, сохраняет кеш и показывает причину. Автоматического повторного запроса на загрузку нет. После восстановления диска нажмите **«Проверить и повторить»** в строке файла.

Устраните причину и нажмите **«Продолжить»** для нового цикла обычных ошибок. Для прерванной передачи в On-premises используйте **«Проверить и повторить»** у файла. Конфликты, изменившиеся исходники и неизвестные исходы кнопка «Продолжить» автоматически не исправляет.

После точечного повтора оставшаяся очередь продолжается автоматически. Если вы сами нажали **«Пауза»**, нажмите **«Продолжить»**. Файлы с неизвестным исходом остаются для отдельной проверки и не мешают обработке оставшегося плана.

Для каждого выбранного файла нужен результат **«Перенесено»** или **«Уже совпадает»**: размер и MD5 назначения должны совпасть с планом. Снятые галочки дают результат **«Пропущен пользователем»**. При повторе из кеша используется сохранённая версия файла; повторного чтения SaaS не требуется. Видимый на Диске файл и состояние всего задания **«Завершено с замечаниями»** не подтверждают перенос всех выбранных файлов. Успех строки «Каталог» означает только создание папки.

Рядом с **«Проверено байтов»** показаны **«Скачивание в кеш»** и **«Загрузка в общий диск»** — скорости за последние примерно пять секунд для способа **«С временным сохранением в кэш»**. «Проверено байтов» увеличивается только после проверки результата.

<a id="onprem-journal"></a>
<a id="подробный-журнал-и-его-выгрузка"></a>
### Журнал и CSV

В **«Журнале задания»** найдите **«Ошибка»**, **«Исход неизвестен»** или **«Прервано»** и сопоставьте соседние события по файлу и ID попытки. Стадия показывает место сбоя: чтение SaaS, публикация, скачивание, создание папки, загрузка в On-premises или проверка результата.

Журнал показывает сторону сбоя, HTTP-статус и код API, если они получены, а также число попыток, паузу, ID операции, время и длительность. Например: **«SaaS: HTTP 500»** или **«On-premises: HTTP 507»**. Для сетевого сбоя без ответа сервера HTTP-статуса нет. Токены и ссылки доступа в журнал и CSV не включаются; имена и пути файлов остаются.

- **«Скачать отчёт CSV»** — текущие результаты файлов и попыток.
- **«Скачать журнал CSV»** — вся сохранённая история задания; на экране видны последние 500 загруженных событий.

CSV: UTF-8 с BOM, разделитель — запятая, `timestamp_utc` — время UTC, размеры — байты, `duration_ms` — миллисекунды. Для диагностики сохраните обе выгрузки: внутренний ID задания остаётся в именах файлов и поле `job_id` журнала CSV.

<a id="onprem-errors"></a>
### Ошибки: что проверить

| Сообщение или код | Действие |
|---|---|
| `onprem_staged_required` | Старое локальное тестовое задание нельзя запустить, продолжить или повторить. Сохраните CSV и создайте новый Dry Run; история и полная остановка доступны |
| `invalid_client`, ошибка авторизации SaaS | Сверьте ID и секрет **одного рабочего** приложения, его регистрацию и права в организации источника |
| `source_admin_auth_failed` | API 360 вернул HTTP 401/403: проверьте админский токен, его доступ к организации и право `directory:read_users` |
| `source_user_not_in_organization` | Email не найден в указанной организации либо получен HTTP 404: проверьте email, ORGID и доступ администратора |
| `source_user_blocked` | Разблокируйте сотрудника в админке и повторите Dry Run; утилита его статус не меняет |
| `source_admin_check_failed` | Проверьте ORGID и подробности в журнале: сеть, HTTP-код или неожиданный ответ API 360 |
| `invalid_grant`, `invalid_request / Unauthorized` | Проверьте ID организации, email и активность сотрудника, регистрацию приложения. Смотрите пояснение сервера: один `invalid_grant` не доказывает отсутствие пользователя |
| Отказ публикации или публичного скачивания | Проверьте `cloud_api:disk.write`, разрешение публичного доступа в организации, пароль и ограничения существующей ссылки. Утилита не снимает эти ограничения |
| HTTP 401 / 403 в On-premises | Получите пользовательский токен из Passport нужной установки; проверьте владельца, OAuth-права и доступ к общему Диску |
| Владелец токена не совпадает | Получите токен под указанным оператором. Для существующего задания нельзя подменить получателя |
| HTTP 400 / 406 / 412 / 415 | Проверьте параметры и код API в журнале; передайте администратору стадию, код и ID запроса. Повтор без исправления запроса может дать тот же результат |
| HTTP 404 | Проверьте источник, метку и путь назначения. Если недоступен общий Диск, восстановите доступ и нажмите «Проверить и повторить» у файла |
| HTTP 409 или «Конфликт» | Путь занят другим содержимым/типом объекта либо отсутствует родительская папка: уточните код API. Проверьте целевой объект с администратором или выберите другой общий диск; автоматической перезаписи нет |
| `stopped_job_path_released` | Прежняя блокировка пути остановленным заданием снята. Нажмите «Продолжить» в задании с этим файлом |
| HTTP 413, `UPLOAD_FILE_SIZE_LIMIT_EXCEEDED` | Размер превышает лимит: уточните ограничения SaaS/установки у администратора |
| HTTP 423, `UPLOAD_TRAFFIC_LIMIT_EXCEEDED` | Уточните код API: блокировка, технические работы, ограничение доступа или трафика. Проверьте права и лимиты с администратором |
| HTTP 429 | Слишком много запросов. Для SaaS дождитесь указанной паузы. Для On-premises устраните ограничение и нажмите «Проверить и повторить» у файла. При частых ошибках снизьте темп запросов |
| HTTP 500 / 502 / 503 / 504 | Ошибка или недоступность сервиса, указанного в журнале. После восстановления On-premises нажмите «Проверить и повторить» у файла; кеш сохраняется |
| HTTP 507, нехватка квоты | Освободите или увеличьте квоту **общего Диска**. Учтите уже полученные файлы и ещё выполняющиеся операции; предупреждение «квота недоступна» не означает, что места достаточно |
| DNS, `connect_failed`, таймаут, HTTP 408, обрыв соединения | Проверьте сеть **из контейнера утилиты**. VPN и сетевой фильтр могут влиять на контейнер отдельно от браузера |
| Ошибка TLS/сертификата | Проверьте адрес, сертификат и корпоративный CA с администратором. Настройка — `ONPREM_CA_BUNDLE`; отключения проверки TLS нет |
| Нет места в локальном кеше | Проверьте свободное место сервера, бюджет кеша и резерв. Приостановите перенос и нажмите «Очистить локальный кеш» либо увеличьте бюджет [ниже](#onprem-admin) |
| `cache_in_use` | Дождитесь завершения текущего действия или подготовки плана. Выполняющийся перенос поставьте на «Паузу» и дождитесь «Приостановлено» либо остановите полностью, затем повторите очистку |
| `cache_cleanup_failed` | Очистка не завершена. Проверьте права на каталог кеша и состояние диска машины утилиты, затем повторите |
| «Источник изменился» | Выберите нужную версию исходника и подготовьте новый план |
| «Проверка недоступна» | Нельзя подтвердить содержимое, например нет MD5. Это не успех; передайте журнал администратору |
| «Ожидание другого задания» | Нажмите «Открыть блокирующее задание». Дайте активному действию завершиться либо нажмите «Остановить полностью». Ошибки и старые неизвестные исходы не удерживают общую очередь |
| HTTP 202 + `invalid_operation_reference` | Запрос принят, но ссылка статуса не распознана. Нажмите «Проверить и повторить» у файла: утилита проверит диск и целевой файл перед новой загрузкой |

У запроса статуса возможен **HTTP 200 с `remote_status=failed`**: запрос выполнен, но серверная операция завершилась ошибкой. Если API не передал причину, журнал так и сообщит. Если причины нет, для диагностики нужны журналы установки.

<a id="onprem-unknown"></a>
<a id="onprem-retry"></a>
### Повтор одного файла

1. В строке файла нажмите **«Проверить и повторить»**. После перезапуска утилиты сначала заполните доступы и подтвердите владельца токена.
2. Утилита проверит права и доступность выбранного общего Диска, включая его корневую папку. Если диск недоступен, повтор сразу завершится конкретной ошибкой; файл в кеше останется.
3. Если целевой файл уже совпадает по размеру и MD5, загрузка не нужна. Иначе утилита проверит кеш и отправит его заново. Частичный файл своей прерванной загрузки может быть заменён; чужие конфликты не перезаписываются.
4. После загрузки утилита проверит размер и MD5 назначения и только затем удалит готовый кеш.

Старая серверная операция повторно не опрашивается. Кнопка также доступна у подходящих файлов с **«Исход неизвестен»**.

Если сохранённый файл кеша утрачен или повреждён, точечный повтор сообщит об этом. После явной очистки кеша через кнопку или при сбое ещё до скачивания утилита получает файл из SaaS заново — для этого нужен доступ к источнику. Ручного ввода ID операции и подтверждения по серверным журналам больше нет.

<a id="onprem-admin"></a>
### Администратору: запуск, доступ и кеш

Готовый образ запускайте по [примеру Docker Compose](https://github.com/cromovsky/yandex-disk-copy/blob/v3.3.0/docs/INSTRUCTION.md#docker-start). Он использует релиз 3.3.0, постоянный том и порт на `127.0.0.1`. Для сборки исходников и локальной HTTP-проверки используйте:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build -d
```

Откройте `http://localhost:8000`. Override разработки разрешает локальный HTTP через `ONPREM_ALLOW_INSECURE_HTTP=1`. Для готового образа это разрешение уже указано в примере Compose. Если задан `ONPREM_ADMIN_TOKEN`, ключ обязателен и локально.

HTTP подходит только для локального стенда: токены между браузером и утилитой не шифруются. В Compose порт по умолчанию опубликован на всех интерфейсах; для локального доступа задайте `127.0.0.1:8000:8000` либо ограничьте его firewall. API назначения всегда требует HTTPS. Для размещения с Caddy нужны настроенные HTTPS/basic-auth и `ONPREM_ADMIN_TOKEN`. Перед запуском готового образа укажите тег `3.3.0` в `image`:

```bash
docker compose -f docker-compose.caddy.yml pull
docker compose -f docker-compose.caddy.yml up -d --no-build
```

Для сборки из исходников вместо этих команд используйте `up --build -d`. Не запускайте оба варианта Compose одновременно. В варианте Caddy не открывайте порт приложения наружу и не разрешайте небезопасный HTTP. Клиенты On-premises не используют прокси из окружения: одной переменной `HTTPS_PROXY` недостаточно.

| Переменная | По умолчанию / назначение |
|---|---|
| `ONPREM_DATA_DIR` | `/var/lib/disk-copy` в Docker, `./migration-data` без Docker: база заданий и подпапка `staging` с кешем; в Docker используется постоянный том `migration-data` |
| `ONPREM_STAGING_MAX_BYTES` | `21474836480` — общий бюджет кеша 20 Гб |
| `ONPREM_STAGING_RESERVE_BYTES` | `1073741824` — резерв свободного места 1 Гб |
| `ONPREM_API_READ_RPS` / `ONPREM_API_WRITE_RPS` | `10` / `2` — темп чтения/изменения API установки |
| `ONPREM_CA_BUNDLE` | Путь к смонтированному PEM-файлу корпоративного CA; без него используются системные доверенные CA |

Чтобы задать **100 Гб кеша и 2 Гб резерва**, добавьте в `.env` рядом с
`docker-compose.yml` (значения — в байтах):

```env
ONPREM_STAGING_MAX_BYTES=107374182400
ONPREM_STAGING_RESERVE_BYTES=2147483648
```

Остановите активные задания и примените настройки к контейнеру:

```bash
docker compose up -d
```

Для локальной сборки с override разработки сохраните оба файла: `docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d`. Для Caddy используйте его файл Compose. Готовый образ не требует override разработки: разрешение локального HTTP задано в его примере Compose.

Compose пересоздаст контейнер; пересборка образа не нужна. План и журнал
сохранятся в томе `migration-data`. Введённые в интерфейсе секреты и токены
потребуется ввести заново.

Лимит общий для временных файлов всех заданий; резерв свободного места
учитывается отдельно. Физического места на диске тоже должно хватать.
Нехватка бюджета или места при скачивании вызывает ошибку
`staging_space_insufficient`. Утилита не удаляет старый кеш для освобождения
бюджета автоматически, в том числе при уменьшении лимита.

Для диска объёмом 1 Тб не нужен кеш на весь терабайт: файлы передаются по одному, готовый кеш удаляется после подтверждённого переноса. Для четырёх одновременных источников бюджет должен вмещать **четыре крупнейших одновременно скачиваемых файла и сохранённые остатки других попыток**; свободное место дополнительно покрывает резерв. Dry Run проверяет этот объём и суммарную квоту назначения. На общем Диске нужна квота для итоговых файлов.

Остановка сохраняет кеш и историю. **«Очистить локальный кеш»** удаляет все файлы из `staging`, в том числе остатки незавершённых попыток и файлы без записи в истории. При продолжении необходимые файлы скачаются заново. История и сведения о серверных операциях сохраняются; исходники, файлы On-premises и локальные копии в `./downloads` не затрагиваются.

Новые задания не создают удалённых технических папок; старые `.disk-copy-transfer-<job-id>` сохраняются. Их можно очистить вручную после подтверждения завершения связанных серверных операций и проверки итогов. Частичные файлы под исходными именами автоматически не удаляются.

Не удаляйте том при пересоздании контейнера: в нём журнал восстановления и планы списков (`source-batches.db`). Перед обновлением сделайте согласованную резервную копию базы и кеша при остановленном приложении. Схема базы — **9**; для отката нужны предыдущий образ и копия до обновления. Один том поддерживает один процесс приложения; несколько workers и NFS не поддерживаются.
