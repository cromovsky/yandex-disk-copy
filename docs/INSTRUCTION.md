<h2 id="saas-access">1. Откуда брать доступы SaaS</h2>

| Поле | Где взять / что указать |
|---|---|
| `CLIENT_ID` и `CLIENT_SECRET` | Карточка рабочего приложения на [oauth.yandex.ru](https://oauth.yandex.ru/). Приложение нужно зарегистрировать как сервисное — порядок ниже |
| `ORGID` | [Админка Яндекс 360](https://admin.yandex.ru/) → «Общие настройки» → «Профиль организации», ID под названием организации |
| `ADMIN_TOKEN` | OAuth-токен администратора организации источника. Получение — шаг 4; необходимость и права — [в таблице ниже](#saas-access-modes) |
| `SOURCE` | Email владельца личного Диска; для локального сохранения общего — email сотрудника с доступом к нему |
| `DESTINATION` | Email получателя; для общего Диска — сотрудника с правом записи |
| `VD_HASH` / `SOURCE_VD_HASH` | Метка общего Диска из его адреса `…/vd/<метка>/…`. Можно вставить метку или весь URL |
| `PATH` | Путь внутри исходного Диска; `/` — весь диск |
| `PAGE_LIMIT` | Число элементов в одном запросе обхода, по умолчанию `1000`. Не ограничивает общее число файлов |

**Email и метка Диска — разные значения.** Не вставляйте ID или `VD_HASH` в
`SOURCE`: утилита получает токен по email сотрудника.

Доступ к SaaS-Диску даёт сервисное приложение, зарегистрированное в организации
источника: по `CLIENT_ID`, `CLIENT_SECRET` и email утилита получает токен
сотрудника. `ORGID` обязателен в форме. Он и `ADMIN_TOKEN` используются для
проверки сотрудника через API 360; в запрос выдачи OAuth-токена они не входят.

<a id="saas-access-modes"></a>
### ADMIN_TOKEN: требования по режимам

| Режим | ADMIN_TOKEN и права | Блокировка сотрудника |
|---|---|---|
| Перенос между SaaS-Дисками; одиночное локальное сохранение | Обязателен: `directory:read_users` и `directory:write_users` | Утилита временно снимает блокировку и восстанавливает её в конце. Если восстановление не удалось, журнал просит заблокировать вручную |
| Локальное сохранение по списку | Необязателен: `directory:read_users` | Автоматической разблокировки нет |
| SaaS → On-premises, один источник или список | Необязателен: `directory:read_users` | Автоматической разблокировки нет |

В списках и SaaS → On-premises указанный ADMIN_TOKEN проверяет email и активность
сотрудника **перед выдачей или обновлением** его токена через
[Directory API](https://yandex.ru/dev/api360/doc/ru/directory/get-users).
Без ADMIN_TOKEN доступ через сервисное приложение сохраняется. Заблокированного
сотрудника разблокируйте в админке, затем повторите Dry Run.
Токены сотрудников обновляются автоматически. При HTTP 401 от API Диска
утилита обновляет токен сотрудника и повторяет запрос один раз.
ADMIN_TOKEN автоматически не обновляется: при ошибке авторизации введите
действующий токен.

Для On-premises нужен отдельный токен сотрудника назначения с доступом к общему
Диску. SaaS ADMIN_TOKEN его не заменяет — см. [инструкцию режима][onprem-guide].

### Шаг 1. Подготовить управляющее приложение

Под владельцем организации [создайте OAuth-приложение](https://oauth.yandex.ru/client/new/)
типа **«Для доступа к API или отладки»** по [инструкции Яндекс ID](https://yandex.ru/dev/id/doc/ru/register-api).
Выдайте права:

- `ya360_security:service_applications_read`;
- `ya360_security:service_applications_write`.

Получите управляющий токен, открыв под владельцем:

```text
https://oauth.yandex.ru/authorize?response_type=token&client_id=<ClientID_управляющего_приложения>
```

Этот токен нужен только для настройки; в форму утилиты его не вставляйте.
В организации должен быть подтверждён почтовый домен и тариф с поддержкой API.

Один раз включите сервисные приложения:

```bash
curl -X POST "https://api360.yandex.net/security/v1/org/<org_id>/service_applications/activate" \
  -H "Authorization: OAuth <управляющий_токен>"
```

### Шаг 2. Создать рабочее приложение для Диска

Создайте **отдельное** OAuth-приложение того же типа.
Выдайте `cloud_api:disk.read`, `cloud_api:disk.write`, `cloud_api:disk.info`.
Скопируйте из его карточки **Client ID** и **Client secret** — это значения
`CLIENT_ID` и `CLIENT_SECRET` в форме.

### Шаг 3. Зарегистрировать рабочее приложение как сервисное

Сначала получите текущий список:

```bash
curl -X GET "https://api360.yandex.net/security/v1/org/<org_id>/service_applications" \
  -H "Authorization: OAuth <управляющий_токен>"
```

**POST заменяет весь список.** Если приложения уже есть, сохраните их ID и права
и передайте вместе с новым. Пример ниже подходит только для пустого списка:

```bash
curl -X POST "https://api360.yandex.net/security/v1/org/<org_id>/service_applications" \
  -H "Authorization: OAuth <управляющий_токен>" \
  -H "Content-Type: application/json" \
  -d '{
    "applications": [{
      "id": "<ClientID_рабочего_приложения>",
      "scopes": ["cloud_api:disk.read", "cloud_api:disk.write", "cloud_api:disk.info"]
    }]
  }'
```

Повторите GET: в ответе должны быть ID рабочего приложения и все три права.
Без регистрации обмен токена может вернуть `400 invalid_request / Unauthorized`.
Описание API: [получить список](https://yandex.ru/dev/api360/doc/ru/ref/ServiceApplicationsService/ServiceApplicationsService_Get),
[заменить список](https://yandex.ru/dev/api360/doc/ru/ref/ServiceApplicationsService/ServiceApplicationsService_Create).

Для проверки доступа к тестовому сотруднику:

```bash
curl -X POST "https://oauth.yandex.ru/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode "grant_type=urn:ietf:params:oauth:grant-type:token-exchange" \
  --data-urlencode "client_id=<ClientID_рабочего_приложения>" \
  --data-urlencode "client_secret=<Client_secret>" \
  --data-urlencode "subject_token=user@yourdomain.ru" \
  --data-urlencode "subject_token_type=urn:yandex:params:oauth:token-type:email"
```

Ожидаемый ответ — `access_token` с `expires_in` около `3600`. При переносе
утилита сама получает и обновляет этот токен; вручную в форму его не вводят.

<a id="шаг-4-получить-admin_token"></a>
### Шаг 4. Получить `ADMIN_TOKEN`

1. Создайте отдельное OAuth-приложение с правами из [таблицы режимов](#saas-access-modes):
   для списков и SaaS → On-premises достаточно `directory:read_users`;
   для остальных режимов добавьте `directory:write_users`.
2. Под администратором организации откройте:

   ```text
   https://oauth.yandex.ru/authorize?response_type=token&client_id=<ClientID_админ_приложения>
   ```

3. Полученный токен вставьте в `ADMIN_TOKEN`. Если изменили права приложения,
   выпустите токен заново.

Официальные инструкции: [сервисные приложения](https://yandex.ru/support/yandex-360/business/admin/ru/security-service-applications),
[доступ к API 360](https://yandex.ru/dev/api360/doc/ru/access).

<h2 id="docker-start">2. Запуск и обновление через Docker</h2>

Нужны Docker 20.10+, Compose v2 и исходящий доступ к `oauth.yandex.ru`,
`cloud-api.yandex.net`, `api360.yandex.net`. Веб-интерфейс использует порт `8000`.

Выберите образ:

- `cromovsky/yandex-disk-copy-v2:3.3.0` — одна или разные SaaS-организации;
- `cromovsky/yandex-disk-copy:3.3.0` — одна SaaS-организация.

В обоих образах доступны локальное сохранение и SaaS → On-premises.

### Docker Compose

Создайте `docker-compose.yml` (ниже образ v2):

```yaml
services:
  disk-copy:
    image: cromovsky/yandex-disk-copy-v2:3.3.0
    ports:
      - "127.0.0.1:8000:8000"
    environment:
      LOCAL_SAVE_DIR: /downloads
      LOCAL_SAVE_HOST_DIR: ./downloads
      ONPREM_DATA_DIR: /var/lib/disk-copy
      # Только для доступа через localhost; при HTTP токены не шифруются.
      ONPREM_ALLOW_INSECURE_HTTP: "1"
      ONPREM_ADMIN_TOKEN: ${ONPREM_ADMIN_TOKEN:-}
      ONPREM_STAGING_MAX_BYTES: ${ONPREM_STAGING_MAX_BYTES:-21474836480}
      ONPREM_STAGING_RESERVE_BYTES: ${ONPREM_STAGING_RESERVE_BYTES:-1073741824}
      ONPREM_API_READ_RPS: ${ONPREM_API_READ_RPS:-10}
      ONPREM_API_WRITE_RPS: ${ONPREM_API_WRITE_RPS:-2}
      DISK_API_TOTAL_RPS: ${DISK_API_TOTAL_RPS:-30}
      DISK_API_READ_RPS: ${DISK_API_READ_RPS:-30}
      DISK_API_WRITE_RPS: ${DISK_API_WRITE_RPS:-3}
      HTTP_TIMEOUT_SEC: ${HTTP_TIMEOUT_SEC:-120}
    volumes:
      - ./downloads:/downloads
      - migration-data:/var/lib/disk-copy
    restart: unless-stopped

volumes:
  migration-data:
```

Запустите готовый образ; сборка из исходников для этого не нужна:

```bash
docker compose pull
docker compose up -d
```

Откройте <http://localhost:8000>. Этот пример разрешает HTTP только для
локального доступа через опубликованный порт `127.0.0.1`. Для удалённого
доступа нужны HTTPS и авторизация; вариант с Caddy описан ниже.

Перед обновлением остановите активную работу и сохраните резервную копию
данных по [гайду обновления](https://github.com/cromovsky/yandex-disk-copy/blob/v3.3.0/docs/UPDATE.md). Журналы доступны в интерфейсе;
для проверки состояния контейнера и веб-сервера:

```bash
docker compose ps
docker compose logs -f disk-copy
```

Остановить контейнер: `docker compose down`. Локальные копии останутся в
`./downloads`, журналы — в томе `migration-data`. Не добавляйте `-v` к команде
остановки: это удалит том с историей. Настройки **SaaS → On-premises** — в
[инструкции режима][onprem-guide].

### Без Compose

```bash
docker pull cromovsky/yandex-disk-copy-v2:3.3.0
docker run -d \
  --name yandex-disk-copy \
  -p 127.0.0.1:8000:8000 \
  -v "$(pwd)/downloads:/downloads" \
  -v migration-data:/var/lib/disk-copy \
  -e LOCAL_SAVE_DIR=/downloads \
  -e LOCAL_SAVE_HOST_DIR="$(pwd)/downloads" \
  -e ONPREM_ALLOW_INSECURE_HTTP=1 \
  --restart unless-stopped \
  cromovsky/yandex-disk-copy-v2:3.3.0
```

### Доступ с других компьютеров через HTTPS

Используйте Caddy с TLS и basic-auth. Для варианта из репозитория:

```bash
cp .env.example .env
# Удвоение $ нужно для корректного чтения хеша в Docker Compose.
docker run --rm caddy:2-alpine caddy hash-password --plaintext 'ВАШ_ПАРОЛЬ' | sed 's/\$/\$\$/g'
```

В `.env` укажите `SITE_ADDRESS`, `BASIC_AUTH_USER` и полученный `BASIC_AUTH_HASH`
(символы `$$` сохраните). Для SaaS → On-premises также задайте
`ONPREM_ADMIN_TOKEN` — отдельный ключ доступа к этому режиму.
Этот Compose использует готовый образ v1. Перед запуском укажите
`image: cromovsky/yandex-disk-copy:3.3.0`; для переноса между организациями —
`image: cromovsky/yandex-disk-copy-v2:3.3.0`. Затем выполните:

```bash
docker compose -f docker-compose.caddy.yml pull
docker compose -f docker-compose.caddy.yml up -d --no-build
```

Для сборки из исходников используйте `up --build -d`; параметр
`build.args.CROSS_ORG_ENABLED` определяет доступность переноса между
организациями в такой сборке.

Публичный домен должен указывать на сервер, порты `80` и `443` — быть доступны:
Caddy получит и будет продлевать сертификат. При `SITE_ADDRESS=localhost`
используется внутренний сертификат, которому браузер по умолчанию не доверяет.
Не запускайте обычный и Caddy Compose одновременно: у них одинаковое имя
контейнера. Не публикуйте порт приложения наружу без TLS и авторизации:
через форму передаются секреты.

<a id="automatic-retries"></a>
### Автоматические повторы

Галочка **«Автоматически повторять при ошибках»** есть во всех режимах,
включая списки дисков, и по умолчанию включена. Её можно менять до запуска
и во время работы; повторный Dry Run не нужен.

Если снять галочку, после первой неудачной попытки утилита пропустит файл
и перейдёт к следующему. В журнале останутся путь, этап, сторона сбоя
(SaaS, On-premises или локальный диск / кеш), причина, HTTP-статус и код API,
если они получены. Ожидающий автоматический повтор отменяется;
уже отправленный запрос завершается или ждёт своего тайм-аута.
Ошибки подготовки доступа и чтения состава исходного каталога показываются
отдельно: без этих данных начать обработку файлов невозможно.
Ручной повтор остаётся доступен; без автоматических повторов он выполняет одну
попытку. Повторное включение галочки действует на последующие ошибки;
пропущенные файлы сами не запускаются.
Настройка и её изменения сохраняются в журнале задания.

Обновление токена после HTTP 401, ограничение частоты запросов и общая пауза
после HTTP 429 сохраняются. Проверка состояния уже принятой сервером операции
продолжается до результата или предусмотренного тайм-аута.

Во всех режимах, включая CSV, после успешной передачи файла утилита ждёт
**20 секунд** перед следующей передачей того же источника. Если автоматические
повторы отключены, после пропуска файла из-за ошибки она также ждёт 20 секунд
перед следующим файлом или папкой. Причина, сторона сбоя и полученные HTTP-код
и код API остаются в журнале. При включённых повторах задержки между попытками
сохраняются. При копировании папки на личный SaaS-Диск сервер копирует её целиком,
затем начинается пауза. Создание папок, исключённые пользователем объекты и уже
существующие файлы новую паузу не запускают. Очередь продолжается автоматически;
параллельные источники ждут независимо. После последнего объекта ожидания нет.

<h2 id="saas-transfer">3. Перенос между SaaS-Дисками</h2>

1. Выберите **«Одна организация»** или **«Между организациями»**.
2. Заполните доступы, `SOURCE`, `DESTINATION` и `PATH` по таблице выше.
   Для разных организаций нужны отдельные `CLIENT_ID` / `CLIENT_SECRET`
   каждой организации. `ORGID` и `ADMIN_TOKEN` — только для источника.
3. Для общего Диска выберите **«Общий диск»**, укажите `VD_HASH` и email
   сотрудника с правом записи в `DESTINATION`.
4. Нажмите **«Запустить перенос»** или **«Запустить перенос между организациями»**.
   Следите за журналом и итоговой сводкой:
   ошибки должны быть разобраны, даже если часть файлов перенеслась.
   Прошлые запуски доступны в истории выбранного режима.

Утилита публикует ресурсы `PATH` и сохраняет их с исходными именами в папку
`<email источника>/…` на Диске получателя. Проверка свободного места включается
через `SPACE_CHECK=1`; по умолчанию она выключена.

**Пакетный перенос:** на вкладке **«Несколько дисков»** скачайте и заполните
шаблон. Для личных Дисков это пары `SOURCE;DESTINATION`, для общего — колонка
`SOURCE` и один получатель с `VD_HASH` в форме. Загрузите файл кнопкой-скрепкой.
Максимум 25 строк, одновременно 5 переносов; `PATH` и тип назначения общие.

API общих Дисков: [обзор](https://yandex.ru/dev/disk-api/doc/ru/reference/shared-disks/shd-overview),
[файлы и папки](https://yandex.ru/dev/disk-api/doc/ru/reference/shared-disks/shdr-overview).

<h2 id="local-save">4. Сохранить локально</h2>

Это отдельная вкладка. Она скачивает файлы без публикации на машину, где
запущена утилита, а не на компьютер с браузером.

1. Введите `CLIENT_ID`, `CLIENT_SECRET`, `ORGID`, `ADMIN_TOKEN` организации
   источника.
2. Выберите тип Диска и заполните:

   | Источник | `SOURCE` | Дополнительное поле | Каталог на машине запуска |
   |---|---|---|---|
   | Личный Диск | Email владельца | — | `./downloads/<email>/…` |
   | Общий диск | Email сотрудника с правом чтения | `SOURCE_VD_HASH`: метка из `…/vd/<метка>/…` или URL | `./downloads/shared/<метка>/…` |

3. Укажите `PATH` (`/` — весь диск) и нажмите **«Сохранить локально»**.
   `PAGE_LIMIT` под полем пути задаёт число элементов в одном запросе,
   а не предел числа сохраняемых файлов.
4. В итогах проверьте **«Сохранено»**, **«Пропущено»** и **«Ошибок»**.
   Точный каталог указан в строке `save_local | на машине запуска`;
   причины ошибок — в журнале.

Каталог должен быть подключён как том (`./downloads:/downloads`), иначе файлы
останутся внутри контейнера. Повторный запуск пропускает локальный файл того же
размера. Готовый файл заменяется только после полного скачивания нового.
Параметры `ONPREM_STAGING_MAX_BYTES` и `ONPREM_STAGING_RESERVE_BYTES` относятся
только к временному кешу SaaS → On-premises: файлы локального сохранения
в `./downloads` ограничены свободным местом на диске машины утилиты.

При HTTP `408`, `429`, `500`, `502`, `503`, `504`, сетевом тайм-ауте или обрыве
при включённых автоматических повторах утилита делает до **5 повторов после первой попытки**: паузы `2, 4, 8, 16, 32`
секунды со случайной добавкой до 25 %. Более длинный корректный `Retry-After`
увеличивает ожидание. Каждый повтор получает новую ссылку и скачивает файл
с начала. После 6 неудачных попыток файл отмечается ошибкой, обработка продолжается.
Ошибки доступа и записи на локальный диск автоматически не повторяются.

### Локальное сохранение по списку

В одном CSV — до **1000 строк с дисками**, без учёта заголовка.
Личные и общие диски можно смешивать. Если строк больше, разделите список
на несколько CSV.

В поле **«Источники»** выберите **«Список дисков из CSV»**. Общие поля —
Client ID, Client secret и **ID организации (ORGID)**. Токен сотрудника утилита
получает через сервисное приложение по email из CSV. **ADMIN_TOKEN** виден и
необязателен: с правом `directory:read_users` проверяет, что email входит в
указанную организацию и сотрудник не заблокирован. Заблокированного сотрудника
нужно разблокировать в админке; Dry Run его статус не меняет.

1. Скачайте шаблон, заполните и загрузите CSV:

   ```csv
   type,email,vd_hash,path
   personal,employee@example.org,,/
   shared,reader@example.org,shared-disk-id,/
   ```

   `personal` — личный диск владельца email; `shared` — общий диск с меткой
   `vd_hash`, доступный сотруднику email. `path` — папка или файл внутри диска;
   `/` — весь диск. ID организации и секреты в CSV не добавляйте.
2. Нажмите **Dry Run**: проверяются доступы, вся структура, размеры, MD5,
   итоговые пути и место для всех выбранных источников. Файлы не скачиваются,
   папки не создаются. Копия личного диска — `downloads/<email>/`, общего —
   `downloads/<название> (<ID>)/`. Название общего диска фиксируется в плане.
3. Устраните ошибки и нажмите **«Повторить Dry Run»** у нужного источника
   либо снимите его галочку. Остальные планы сохраняются.
4. В **«Файлы»** снимите галочки с ненужных объектов, затем нажмите **«Начать сохранение»**.
   Одновременно работают максимум четыре источника во всей утилите,
   по одному файлу на источник.
   Пауза, продолжение и полная остановка управляют всем выбранным списком.

Все файлы и папки после полного Dry Run отмечены по умолчанию. Снятие галочки
с папки исключает всё её содержимое, включая другие страницы плана; выбор вложенного
файла включает нужные родительские папки. Исключённые объекты не попадают
в очередь, не считаются ошибками и не повторяются. Выбор сохраняется после
обновления страницы и перезапуска контейнера и не требует нового Dry Run;
менять его можно до первого запуска сохранения. Без выбранных объектов запуск
недоступен, источник с пустым выбором пропускается. Выбор отдельных объектов
доступен в списках CSV и [SaaS → On-premises][onprem-guide].

**«Остановить полностью»** во время Dry Run прекращает обход и дальнейшие
повторы запросов. Нажмите **Dry Run** или **«Начать заново»** для нового списка;
история остановленной проверки сохраняется. Уже отправленный HTTP-запрос
может завершаться до сетевого тайм-аута; новые источники ждут свободного слота.

В режиме списков совпадение подтверждается **размером и MD5**. Другое содержимое
не перезаписывается; отсутствие MD5 отмечается как недоступная проверка.
При прерванном обходе старт заблокирован, пока Dry Run не завершится полностью.
План фиксирует состав файлов: новые файлы попадут только в новый Dry Run,
изменившиеся исходники требуют повторного планирования.

**«Файлы»** показывает план источника, **«Подробный журнал»** — стадии и ошибки;
выгрузки **«Скачать план CSV»** и **«Скачать журнал CSV»** объединяют список.
История и очередь хранятся в томе `migration-data`. После перезапуска введите
Client secret и, если использовали, ADMIN_TOKEN заново; секреты на диск не
записываются. Нажмите **«Продолжить»** для восстановления доступа и продолжения
прерванной работы. Если план готов, но ещё не запускался, затем нажмите
**«Начать сохранение»**.
Для окончательно остановленного списка используйте **«Начать заново»**.

<h3 id="saas-journal">Журнал, история запусков и CSV</h3>

В режимах **«Одна организация»**, **«Между организациями»** и
**«Сохранить локально»** каждый запуск сохраняется отдельно с датой и временем.
Выберите запуск в истории своего режима; обновление страницы и перезапуск
контейнера не удаляют журнал. В пакете события привязаны к конкретной паре
источник → получатель.

Журнал показывает:

- **Где и на каком этапе сбой:** SaaS-источник, SaaS-получатель или локальный
  диск; публикация, создание папки, скачивание, загрузка, ожидание операции
  и доступная в этом режиме проверка результата.
- **Причину:** HTTP-код, код API и ID запроса, если сервер их вернул;
  DNS, TLS, тайм-аут, обрыв соединения или ошибка локальной записи.
- **Дальнейшее действие:** номер попытки, задержку, пропуск или неизвестный
  исход. **«Не подтверждено»** означает, что сервер принял загрузку, но её
  завершение не подтверждено. Такие файлы не учитываются в **«Сохранено»**.
  Подтверждение операции сервером не означает проверку MD5 содержимого.

На экране — последние **500 событий**. **«Скачать журнал CSV»** выгружает всю
сохранённую историю выбранного запуска: UTF-8 с BOM, запятые, время UTC.
В интерфейсе время соответствует часовому поясу браузера. Токены и ссылки
доступа не сохраняются; имена файлов, пути и email участников переноса остаются.

**«Очистить журнальный кеш»** внизу удаляет историю **только открытого режима**.
Выполняющийся перенос этого режима нужно дождаться. Скачанные файлы, кеш
содержимого и история SaaS → On-premises не затрагиваются.

После перезапуска незавершённый запуск получает **«Прервано»** и автоматически
не повторяется. Принятая SaaS операция может продолжаться: при неизвестном
исходе проверьте файлы на целевом Диске перед новым переносом. Журналы запусков,
выполненных до появления этой функции, восстановить нельзя.

В Docker журналы находятся в `/var/lib/disk-copy/journals/history.db`
на постоянном томе `migration-data`; без Docker — в
`./migration-data/journals/history.db`. Корень задаёт `ONPREM_DATA_DIR`,
хранение работает и при выключенном режиме On-premises. Сохраняйте том при
обновлении; общий доступ к утилите открывает и историю запусков.

<h2 id="saas-errors">5. Ошибки SaaS-переноса и локального сохранения</h2>

| Сообщение / симптом | Что проверить и сделать |
|---|---|
| `400 invalid_request / Unauthorized` | Зарегистрируйте рабочее приложение как сервисное (шаг 3) |
| `invalid_client`, ошибка получения токена | Возьмите ID и секрет из одной карточки рабочего приложения; проверьте его регистрацию |
| `invalid_grant` | Проверьте email и активность сотрудника, организацию и регистрацию сервисного приложения; в `SOURCE` нужен email, а не ID общего Диска |
| Ошибка проверки статуса сотрудника | Проверьте `ORGID`, `ADMIN_TOKEN` и права `directory:read_users`, `directory:write_users` |
| `source_admin_auth_failed` | API 360 вернул HTTP 401/403: проверьте токен администратора, его доступ к организации и `directory:read_users` |
| `source_user_not_in_organization` | Email не найден в указанной организации либо получен HTTP 404: проверьте email, `ORGID` и доступ администратора |
| `source_user_blocked` | Разблокируйте сотрудника в админке и повторите Dry Run; список сам его не разблокирует |
| `source_admin_check_failed` | Проверьте `ORGID` и подробности в журнале: сеть, HTTP-код или неожиданный ответ API 360 |
| HTTP `403` при чтении информации о Диске | Проверьте права `cloud_api:disk.info` и доступ сотрудника. Если включали `SPACE_CHECK=1`, посмотрите выданные `scope` в строке `get_token` |
| Недостаточно места | Освободите место на выбранном Диске или машине запуска |
| HTTP `429` | Утилита ждёт автоматически. При частых ответах снизьте темп запросов |
| HTTP `5xx`, тайм-аут или обрыв при локальном скачивании | Если автоматические повторы включены, дождитесь их завершения. Для файла с ошибкой проверьте сеть и повторите сохранение |
| DNS, TLS, тайм-аут или обрыв | Смотрите сторону и этап сбоя; проверьте сеть из контейнера, адреса и сертификаты |
| «Исход неизвестен» | Сервер не подтвердил результат. Проверьте целевой Диск и состояние серверной операции перед новым переносом |
| `journal_in_use` | В этом режиме ещё идёт перенос; очистите журнальный кеш после его завершения |
| `journal_write_failed` | Журнал может быть неполным. Проверьте свободное место и права на каталог журналов |
| Файлы не появились на компьютере с браузером | Они сохраняются на машине запуска. Проверьте каталог в логе и подключение `downloads` |
| Страница не открывается на `8000` | Проверьте `docker compose ps`, `docker compose logs` и доступность порта |

Для ошибок **SaaS → On-premises**, точечных повторов и полной остановки —
[инструкция этого режима][onprem-guide].

### Темп запросов

Официальный предел SaaS Disk API — [40 запросов/с](https://yandex.ru/legal/disk_api/ru/).
Утилита по умолчанию использует общий бюджет **30 запросов/с**, в том числе
не более **3 изменений/с**, на весь процесс. Текущие значения указаны в строке `RATE LIMIT`. При частых
`429` добавьте в `environment` Compose и пересоздайте контейнер:

```yaml
DISK_API_TOTAL_RPS: "20"
DISK_API_READ_RPS: "20"
DISK_API_WRITE_RPS: "2"
```

`HTTP_TIMEOUT_SEC` задаёт тайм-аут чтения ответа (по умолчанию 120 секунд,
соединения — 10 секунд). Несколько процессов или контейнеров не делят этот
лимит между собой. Лимиты On-premises настраиваются отдельно.
