# Инструкция: перенос файлов между Дисками сотрудников Яндекс 360

Документ для администраторов организаций. Состоит из двух частей:

1. **Настройка сервисного приложения** — подготовка доступа к Дискам через API.
2. **Запуск инструмента** — развёртывание из Docker Hub и работа через веб-интерфейс.

> **Важно: статус инструмента и ответственность**
>
> Это **не готовое продуктовое решение Яндекса** и не часть официальной поставки
> Яндекс 360. Инструмент и данная инструкция предоставляются «как есть» (*as is*) —
> вспомогательные материалы для администраторов, которые самостоятельно решают
> задачу переноса файлов между Дисками сотрудников.
>
> Вы можете использовать их на свой страх и риск. Все риски, связанные с запуском,
> настройкой и эксплуатацией — в том числе потеря или дублирование файлов, простой
> Диска, нарушение внутренних политик безопасности, некорректная работа при
> изменении API или лимитов — несёт организация, выполняющая перенос.
>
> Перед боевым запуском:
> - протестируйте на одной паре сотрудников и небольшой папке;
> - согласуйте использование сервисных приложений с политиками ИБ и юридической службой;
> - убедитесь, что получено необходимое согласие пользователей на доступ к их Диску
>   (см. справку по сервисным приложениям).
>
> Официальная поддержка Яндекс 360 **не распространяется** на этот инструмент.

---

## Что делает инструмент

Копирует файлы с Диска одного сотрудника на Диск другого **в пределах одной
организации** Яндекс 360:

- получает доступ к Дискам сотрудников через сервисное приложение (token-exchange
  по email, без ввода паролей);
- публикует ресурсы исходной папки и сохраняет их в **отдельную папку** на Диске
  получателя (названа по email источника, напр. `disk:/user@company1.ru`) с
  **оригинальными** именами файлов;
- перед копированием сверяет занятое место источника со свободным на Диске
  получателя;
- если сотрудник-источник заблокирован, временно разблокирует его на время
  копирования и возвращает блокировку в конце (даже при ошибке).

> **Два режима работы (v2):**
> - **Одна организация** — источник и получатель в одной орге, один сервис-аккаунт.
> - **Между организациями** — источник и получатель в разных оргах; в каждой орге
>   свой сервис-аккаунт (см. раздел «Режим 2» ниже).
>
> Образ **`cromovsky/yandex-disk-copy-v2`** содержит оба режима. Образ
> **`cromovsky/yandex-disk-copy`** (v1) — только режим «одна организация».

## Часть 1. Создание и настройка сервисного приложения

### Зачем это нужно

Чтобы читать Диск источника и писать на Диск получателя без ввода паролей
сотрудников, в организации регистрируется **сервисное приложение** — отдельное
OAuth-приложение с правами на Диск, привязанное к организации.

Полное описание механизма и примеры запросов — в официальной справке:
[Сервисные приложения](https://yandex.ru/support/yandex-360/business/admin/ru/security-service-applications).

> После подключения сервисных приложений администратор обязан уведомить
> пользователей и при необходимости получить их согласие (п. 3.6 оферты).

### Что понадобится

| Требование | Комментарий |
|------------|-------------|
| Тариф | Должен поддерживать работу с API |
| Роль | Владелец организации или администратор с правом управлять OAuth-приложениями |
| Почтовый домен | Должен быть подключён и подтверждён в организации |
| Количество приложений | До 20 сервисных приложений на организацию |

### Общая схема (три набора доступов на организацию)

```
┌─────────────────────────────────────────────────────────────┐
│ Приложение A — «управляющее» (один раз на организацию)       │
│ Scopes: ya360_security:service_applications_read/write       │
│ Назначение: активировать функцию и зарегистрировать          │
│             сервисные приложения в организации               │
└─────────────────────────────────────────────────────────────┘
            │
            ▼
┌─────────────────────────────────────────────────────────────┐
│ Приложение B — «рабочее» (доступ к Дискам)                   │
│ Scopes: cloud_api:disk.read, cloud_api:disk.write,           │
│         cloud_api:disk.info                                  │
│ Назначение: token-exchange → доступ к Дискам сотрудников     │
│ → Client ID и Client secret передаются в инструмент          │
└─────────────────────────────────────────────────────────────┘
            +
┌─────────────────────────────────────────────────────────────┐
│ Админ-токен — блокировка/разблокировка сотрудника            │
│ Scopes: directory:read_users, directory:write_users          │
│ Назначение: проверить статус и временно разблокировать       │
│             заблокированного источника                       │
│ → OAuth-токен передаётся в инструмент (поле ADMIN_TOKEN)     │
└─────────────────────────────────────────────────────────────┘
```

**Важно:** приложение B — это **отдельное** OAuth-приложение, не то же, что
приложение A. Именно **Client ID и Client secret приложения B** передаются в
инструмент (поля `CLIENT_ID` / `CLIENT_SECRET`). Управляющее приложение A и его
токен в инструмент **не передаются** — они нужны только на этапе настройки.

### Шаг 1. Создать управляющее OAuth-приложение

1. Войдите под **владельцем организации**.
2. Откройте страницу создания OAuth-приложения.
3. Заполните форму:
   - **Название** — любое понятное (например, `Service Apps Manager`).
   - **Платформы** — «Веб-сервисы».
   - **Redirect URI** — нажмите «Подставить URL для отладки».
   - **Доступ к данным** — добавьте:
     - `ya360_security:service_applications_read`
     - `ya360_security:service_applications_write`
4. Укажите email для связи и нажмите **Создать приложение**.
5. Скопируйте **ClientID** — он понадобится на следующем шаге.

Подробнее: [Доступ к API Яндекс 360](https://yandex.ru/dev/api360/doc/ru/access).

### Шаг 2. Получить OAuth-токен владельца (управляющий токен)

Перейдите по ссылке (подставьте ClientID из шага 1):

```
https://oauth.yandex.ru/authorize?response_type=token&client_id=<ClientID_управляющего_приложения>
```

После авторизации скопируйте токен со страницы. Сохраните его в надёжном месте —
он нужен только для настройки, не для самого инструмента.

> Токен не отображается повторно. При потере получите новый по той же ссылке.

### Шаг 3. Активировать сервисные приложения в организации

Выполните один раз для организации. Подставьте `org_id` (идентификатор организации
из админки Яндекс 360) и управляющий токен:

```bash
curl -X POST "https://api360.yandex.net/security/v1/org/<org_id>/service_applications/activate" \
  -H "Authorization: OAuth <управляющий_токен>"
```

Успешный ответ подтверждает, что функция включена.

### Шаг 4. Создать рабочее OAuth-приложение для Диска

1. Снова откройте создание OAuth-приложения.
2. Создайте **новое** приложение (не редактируйте управляющее):
   - **Название** — например, `Disk Transfer Service App`.
   - **Платформы** — «Веб-сервисы», **Redirect URI** — «Подставить URL для отладки».
   - **Доступ к данным** — добавьте:
     - `cloud_api:disk.read` — чтение Диска;
     - `cloud_api:disk.write` — запись на Диск получателя;
     - `cloud_api:disk.info` — информация о свободном месте.
3. Сохраните приложение.
4. Скопируйте **идентификатор приложения (Client ID)** и **секрет приложения** —
   эту пару вы передадите в инструмент (`CLIENT_ID` / `CLIENT_SECRET`).

### Шаг 5. Зарегистрировать рабочее приложение как сервисное

```bash
curl -X POST "https://api360.yandex.net/security/v1/org/<org_id>/service_applications" \
  -H "Authorization: OAuth <управляющий_токен>" \
  -H "Content-Type: application/json" \
  -d '{
    "applications": [{
      "id": "<ClientID_рабочего_приложения>",
      "scopes": [
        "cloud_api:disk.read",
        "cloud_api:disk.write",
        "cloud_api:disk.info"
      ]
    }]
  }'
```

> Без шага 5 token-exchange возвращает `400 invalid_request / Unauthorized`.

### Шаг 6. Проверить регистрацию

```bash
curl -X GET "https://api360.yandex.net/security/v1/org/<org_id>/service_applications" \
  -H "Authorization: OAuth <управляющий_токен>"
```

В ответе должно быть ваше приложение со scopes `cloud_api:disk.read`,
`cloud_api:disk.write`, `cloud_api:disk.info`.

Опционально — проверить обмен токена (token-exchange) для тестового сотрудника
(подставьте идентификатор и секрет рабочего приложения и email пользователя):

```bash
curl -X POST "https://oauth.yandex.ru/token" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  --data-urlencode "grant_type=urn:ietf:params:oauth:grant-type:token-exchange" \
  --data-urlencode "client_id=<ClientID_рабочего_приложения>" \
  --data-urlencode "client_secret=<Client_secret>" \
  --data-urlencode "subject_token=user@yourdomain.ru" \
  --data-urlencode "subject_token_type=urn:yandex:params:oauth:token-type:email"
```

В ответе должен быть `access_token` с `expires_in` около 3600 секунд.

### Шаг 7. Получить административный токен для блокировки/разблокировки

У заблокированного сотрудника нельзя выпустить токен Диска. Инструмент проверяет
статус источника и при необходимости временно разблокирует его, поэтому нужен
OAuth-токен с правом управления сотрудниками.

1. Зарегистрируйте **отдельное** OAuth-приложение на `https://oauth.yandex.ru`
   со scopes:
   - `directory:read_users` — проверка статуса сотрудника;
   - `directory:write_users` — блокировка / разблокировка.
2. Под учётной записью **администратора организации** откройте (подставьте ClientID):
   ```
   https://oauth.yandex.ru/authorize?response_type=token&client_id=<ClientID_админ_приложения>
   ```
3. Скопируйте выданный токен — это значение `ADMIN_TOKEN` в инструменте. При
   изменении прав приложения токен нужно выпустить заново.

### Что указать в интерфейсе (блок «Сервисное приложение и организация»)

После настройки заполните на странице инструмента:

| Поле в интерфейсе | Значение |
|-------------------|----------|
| `CLIENT_ID` | Client ID рабочего приложения (шаг 4) |
| `CLIENT_SECRET` | секрет рабочего приложения (шаг 4) |
| `ORGID` | идентификатор организации |
| `ADMIN_TOKEN` | OAuth-токен со scopes `directory:*_users` (шаг 7) |
| `SOURCE` | email сотрудника, с Диска которого копируем |
| `DESTINATION` | email сотрудника-получателя **или** (для общего диска) сотрудника с правом записи |
| Тип назначения | **Личный Диск** / **Общий диск** |
| `VD_HASH` | метка общего диска из URL (`…/vd/<метка>/…`); только если выбран общий диск |
| `PATH` | папка на Диске источника (`/` — корень) |
| `PAGE_LIMIT` | размер страницы при обходе (по умолчанию `1000`) |

#### Перенос на общий диск

1. В форме выберите **«Общий диск»**.
2. Укажите `VD_HASH` — откройте общий диск в [disk.yandex.ru](https://disk.yandex.ru),
   в адресной строке будет фрагмент `/vd/<метка>/`. Можно вставить метку или весь URL.
3. В `DESTINATION` укажите email сотрудника, которому выдан доступ к этому общему
   диску с правом **редактирования** (запись). Перенос идёт от его имени.
4. Файлы появятся в папке `<email источника>/…` на общем диске.
5. В пакетном режиме (вкладка «Несколько дисков») список содержит только источники;
   `DESTINATION` и `VD_HASH` один на весь пакет — все источники уходят на этот
   общий диск.

Документация API общих дисков:
[Общие диски](https://yandex.ru/dev/disk-api/doc/ru/reference/shared-disks/shd-overview),
[файлы и папки](https://yandex.ru/dev/disk-api/doc/ru/reference/shared-disks/shdr-overview).

> Управляющее приложение A и его токен в инструмент **не передаются** — они нужны
> только на этапе настройки (шаги 1–6).

В интерфейсе доступна кнопка **«?»** с этой же справкой; ссылки, права и тела
запросов в ней копируются по клику.

## Режим 2. Перенос между организациями

Сервисное приложение выпускает токены только для пользователей своей организации,
поэтому для переноса между разными оргами нужен **свой сервис-аккаунт в каждой**.

1. Выполните **Часть 1 дважды** — отдельно в организации-источнике и в
   организации-получателе (у каждой свои `CLIENT_ID` / `CLIENT_SECRET`).
2. `ADMIN_TOKEN` нужен **только для организации-источника** (разблокировка
   уволенного сотрудника). Получатель считается активным — у него `ADMIN_TOKEN`
   и `ORGID` не требуются.

На вкладке **«Между организациями»** заполните:

| Поле | Значение |
|------|----------|
| Источник · `CLIENT_ID` / `CLIENT_SECRET` | сервис-аккаунт орг-источника |
| Источник · `ORGID` | идентификатор организации-источника |
| Источник · `ADMIN_TOKEN` | токен со scopes `directory:*_users` орг-источника |
| Источник · `SOURCE` | email сотрудника-источника |
| Получатель · `CLIENT_ID` / `CLIENT_SECRET` | сервис-аккаунт орг-получателя |
| Получатель · `DESTINATION` | email сотрудника-получателя или (общий диск) сотрудника с правом записи |
| Тип назначения / `VD_HASH` | личный Диск или общий диск орг-получателя |
| `PATH` / `PAGE_LIMIT` | как в режиме одной организации |

Механика та же: ресурсы источника публикуются и сохраняются через публичные
ссылки в отдельную папку на Диске получателя (по email источника) с оригинальными
именами.

## Часть 2. Запуск инструмента из Docker Hub

**Образ в Docker Hub:** `cromovsky/yandex-disk-copy:latest`

> Для режима «между организациями» используйте образ
> **`cromovsky/yandex-disk-copy-v2:latest`** — в нём есть обе вкладки. Команды ниже
> показаны для v1; для v2 подставьте `-v2` в имя образа
> (`cromovsky/yandex-disk-copy-v2:latest`).

### Требования к серверу

| Компонент | Версия |
|-----------|--------|
| Docker | 20.10+ |
| Docker Compose | v2 (рекомендуется) |
| Сеть | Исходящий доступ к `oauth.yandex.ru`, `cloud-api.yandex.net`, `api360.yandex.net` |
| Порт | `8000` (веб-интерфейс) |

### Вариант A. Быстрый запуск через `docker run`

```bash
docker pull cromovsky/yandex-disk-copy:latest

docker run -d \
  --name yandex-disk-copy \
  -p 8000:8000 \
  --restart unless-stopped \
  cromovsky/yandex-disk-copy:latest
```

Откройте в браузере: `http://<IP-сервера>:8000`

> Инструмент не хранит данные между запусками: токены вводятся в форме каждый раз,
> логи стримятся в браузер. Том данных не требуется.

### Вариант B. Запуск через Docker Compose (рекомендуется)

Создайте файл `docker-compose.yml`:

```yaml
services:
  disk-copy:
    image: cromovsky/yandex-disk-copy:latest
    ports:
      - "8000:8000"
    restart: unless-stopped
```

Запуск:

```bash
docker compose pull
docker compose up -d
```

Проверка:

```bash
docker compose ps
docker compose logs -f disk-copy
```

Остановка:

```bash
docker compose down
```

### Защищённый доступ: reverse-proxy Caddy с TLS и авторизацией (рекомендуется при выносе наружу)

Если инструмент выносится за пределы `localhost`, поднимайте его за reverse-proxy
с TLS и basic-auth. Секреты (`CLIENT_SECRET`, `ADMIN_TOKEN`) вводятся в форме и без
TLS передаются открыто — не публикуйте порт `8000` наружу без авторизации.

Готовый образ Caddy с автоматическим HTTPS и basic-auth опубликован в Docker Hub:
**`cromovsky/yandex-disk-copy-caddy:latest`** (Caddyfile зашит, локальная сборка не
нужна). Сам сервис при этом наружу не публикуется — только через Caddy.

1. Создайте `.env` (логин и bcrypt-хеш пароля):
   ```bash
   # sed удваивает $ → $$, иначе docker compose съест часть хеша
   docker run --rm caddy:2-alpine caddy hash-password --plaintext 'ВАШ_ПАРОЛЬ' | sed 's/\$/\$\$/g'
   ```
   ```ini
   # .env
   SITE_ADDRESS=disk.example.com   # публичный домен (или localhost для проверки)
   BASIC_AUTH_USER=admin
   BASIC_AUTH_HASH=<строка из команды выше, символы $$ оставьте как есть>
   ```

2. Создайте `docker-compose.yml`:
   ```yaml
   services:
     disk-copy:
       image: cromovsky/yandex-disk-copy:latest
       restart: unless-stopped
       expose:
         - "8000"
     caddy:
       image: cromovsky/yandex-disk-copy-caddy:latest
       restart: unless-stopped
       ports:
         - "80:80"
         - "443:443"
         - "443:443/udp"
       env_file: .env
       volumes:
         - caddy_data:/data
         - caddy_config:/config
       depends_on:
         - disk-copy
   volumes:
     caddy_data:
     caddy_config:
   ```

3. Запуск:
   ```bash
   docker compose pull
   docker compose up -d
   ```

- `SITE_ADDRESS=localhost` — Caddy выдаёт self-signed сертификат внутреннего CA
  (для проверки; браузер предупредит — это нормально).
- `SITE_ADDRESS=<публичный домен>` — домен должен резолвиться на сервер, порты
  80/443 быть доступны снаружи; Caddy сам получит и продлит сертификат Let's
  Encrypt. Сертификаты хранятся в томе `caddy_data`.

## Работа в веб-интерфейсе

1. Откройте `http://<IP-сервера>:8000`.
2. Заполните форму:
   - блок **«Сервисное приложение и организация»** — `CLIENT_ID`, `CLIENT_SECRET`,
     `ORGID`, `ADMIN_TOKEN`;
   - блок **«Источник, назначение и параметры»** — `SOURCE`, `DESTINATION`,
     `PATH`, `PAGE_LIMIT`.
3. Нажмите **«Запустить перенос»**.
4. Следите за **живым логом** под формой: статус каждого шага (получение токенов,
   проверка статуса сотрудника, сверка места, публикация и сохранение ресурсов).
   По завершении появится статус **«Готово ✓»**, при ошибке — текст ошибки.

### Пакетный перенос (несколько дисков)

1. Откройте вкладку **«Несколько дисков»**.
2. Выберите тип назначения:
   - **Личный Диск** — скачайте шаблон пар `SOURCE;DESTINATION`, заполните до 25 пар;
   - **Общий диск** — скачайте шаблон источников (колонка `SOURCE`), укажите один
     `DESTINATION` (сотрудник с правом записи) и `VD_HASH`. Все источники из списка
     переносятся на этот общий диск.
3. Загрузите файл кнопкой-скрепкой.
4. PATH и тип назначения общие для всего пакета; одновременно идут **5** переносов.
5. В логе у каждой строки префикс `[N/M source → destination]`.

Что происходит под капотом:

1. Инструмент получает токен источника (token-exchange по email).
2. Проверяет статус сотрудника-источника; если заблокирован — временно
   разблокирует.
3. Сверяет занятое место источника со свободным на Диске получателя.
4. Публикует все ресурсы в `PATH` и собирает публичные ссылки.
5. Создаёт на Диске получателя отдельную папку (по email источника) и сохраняет
   ресурсы туда с оригинальными именами.
6. Возвращает исходную блокировку сотрудника (даже при ошибке).

## Типичные ошибки

| Симптом | Причина | Что сделать |
|---------|---------|-------------|
| `400 invalid_request / Unauthorized` при получении токена | Рабочее приложение не зарегистрировано как сервисное в организации | Повторить шаг 5 |
| `Wrong client secret` / отказ авторизации | Client ID и секрет от разных приложений | Взять пару с одной страницы `oauth.yandex.ru` |
| `Недостаточно места на диске назначения` | Свободного места получателя меньше занятого у источника | Освободить место или выбрать другого получателя |
| Ошибка при проверке статуса сотрудника | Нет/неверный `ADMIN_TOKEN` или у него нет `directory:*_users` | Перевыпустить токен по шагу 7 |
| Контейнер не открывается на `8000` | Порт занят или межсетевой экран | `docker compose logs`, проверить firewall |
| Файлы не там, где ожидали | Так и задумано: ресурсы попадают в отдельную папку `disk:/<email источника>` на Диске получателя (оригинальные имена) | — |
| В логе строки `429 \| ... общая пауза N с` | Упёрлись в лимит частоты запросов API Диска | Инструмент притормаживает сам и повторяет. Если таких строк много — снизить темп: `DISK_API_RPS=10` (см. ниже) |
| Пакетный перенос идёт медленно, лог «капает» | Так и задумано: запросы к API Диска ограничены темпом | Норма. Текущий темп — в строке `RATE LIMIT` в начале лога |

### Темп запросов к API Диска

Условия использования API Диска (п. 2.2) декларируют максимум **40 запросов в
секунду** на сервис; при превышении доступ может быть ограничен или прекращён.
Инструмент держит суммарный темп ниже потолка сам — по умолчанию 20 запросов/с,
общих на все параллельные переносы. Ручки (перезапуск без пересборки образа):

```bash
docker run -e DISK_API_RPS=10 -p 8000:8000 cromovsky/yandex-disk-copy-v2
```

Через Compose — переменные `DISK_API_RPS` и `HTTP_TIMEOUT_SEC` в `.env`.
