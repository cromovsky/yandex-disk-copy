# Стенд и проверка переноса SaaS → on-premises

Дата: 11 октября 2026 года.
Связанный проект: `2026-10-11-saas-to-onprem-design.md`.
Статус: сценарии будущих проверок; реальные переносы ещё не выполнялись.

## Что подготовить на стенде

- Версия инсталляции и адрес API; адрес passport для выдачи OAuth.
- Один отдельный пользователь назначения с личным Диском и известной квотой.
- Client ID от администратора и пользовательский токен назначения.
- Возможность подтвердить identity токена поддерживаемым API или администратором.
- Доверенный CA для контейнера утилиты, если используется корпоративный сертификат.
- Доступ контейнера к API/uploader/downloader on-premises и SaaS.
- Отдельно: исходящий доступ самого downloader on-premises к скачиванию SaaS.
- Одноразовый каталог назначения и отдельный source-пользователь с тестовыми
  файлами; без необходимости переносить рабочие пользовательские данные.
- Доступ администратора к журналам on-premises для проверки операций, чей
  идентификатор потерялся вместе с HTTP-ответом.
- Возможность перезапустить контейнер утилиты и временно прервать соединение
  тестового клиента/прокси, не меняя сетевые правила всей инсталляции.

Токены и приватные ссылки передаются непосредственно в тестовую утилиту.
В этот документ, переписку и отчёт помещаются только безопасные идентификаторы
и результаты. Адреса и версии добавляются после получения фактуры стенда.

## Набор файлов

| Файл/дерево | Назначение |
|---|---|
| Пустой файл и файл в несколько килобайт | Базовая передача и нулевой размер |
| Вложенное дерево и пустая папка | Структура и создание каталогов |
| Имя с пробелами, кириллицей, `+`, `%`, `#` | URL-кодирование и path mapping |
| Файлы `report` и `report.part` | Независимость spool от пользовательских имён |
| Файл больше 512 МиБ | Отсутствие ограничения старого memory fallback |
| Файл 25 ГБ, если позволяют квоты и стенд | Долгая операция, staging и стабильный расход памяти |
| Одинаковое имя с другим содержимым в назначении | Конфликт без перезаписи |
| Одинаковый размер, но другие байты | Недостаточность проверки только размера |
| Файл, изменяемый после создания плана | Выявление смены исходной версии |

Размеры большого теста выбираются по возможностям стенда. Если тест 25 ГБ не
выполнен, отчёт не заявляет проверку этого размера. Для каждого файла заранее
известны размер и MD5; локально можно дополнительно сохранить SHA-256.

## Сначала подтвердить контракты

| ID | Проверка | Ожидаемое доказательство |
|---|---|---|
| C01 | OAuth и владелец получателя | Токен относится к нужному тестовому Диску |
| C02 | Частная ссылка владельца SaaS → on-prem POST URL | `202`, сохранённый ref, терминальный `success`, совпавший MD5 |
| C03 | GET upload → PUT | `201` либо `202` с корректным polling; файл проверен |
| C04 | Создание технического каталога и move | Итоговый файл перенесён с `overwrite=false` |
| C05 | Итоговый путь занят до move | `409`/конфликт; прежние байты и hash неизменны |
| C06 | Путь занят непосредственно во время финализации | Нет перезаписи при гонке; исход установлен |
| C07 | Метаданные, квота, ограничения | Наблюдаемые поля и ошибки соответствуют фактической версии |

Основной способ считается подтверждённым только после C02. Без C05/C06
обычные пользовательские папки не допускаются к пилотному выпуску.

## Восстановление и ошибки

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| R01 | POST мог быть принят, ответ потерян до сохранения ref | `outcome_unknown`; нет автоматической повторной отправки |
| R02 | Перезапуск после сохранения ref | Повтор доступов, polling прежней операции; нет нового import |
| R03 | Перезапуск во время проверки файла | Проверка продолжается; `done` до неё отсутствует |
| R04 | Ответ move потерян | Reconciliation; один факт существования пути не считается успехом |
| R05 | Операция продолжает работу дольше лимита наблюдения | Остаётся ожидающей; не становится failed по одному таймеру |
| R06 | Операция завершилась `failed` | Ручной повтор создаёт новый attempt/technical path |
| R07 | Ссылка истекла или on-premises не видит SaaS | Установленная ошибка; режим автоматически не меняется |
| R08 | Ручной повтор URL-ошибки способом staged | Успех проверен; обе попытки отражены в журнале |
| R09 | Разрыв скачивания в staged | Частичный собственный объект не принят за полный файл |
| R10 | Разрыв PUT после передачи тела | Сверка результата перед повтором; handle открывается заново |
| R11 | Недостаток квоты назначения/локального места | Понятная ошибка; существующие пользовательские файлы сохранены |
| R12 | Источник изменён/удалён | `source_changed`/ошибка; неподтверждённая версия не финализирована |
| R13 | Wrong-user credentials после restart | Reattach отклонён; итоговые пути задания не изменены |
| R14 | Пауза во время server-pull | Нет новых файлов; активная операция сохранена и видна |
| R15 | Переподключение SSE | Replay событий по sequence без потери/разрушающего чтения |
| R16 | Очистка при active/outcome_unknown | Активные и неопределённые технические попытки сохранены |
| R17 | Источник изменился, но назначение совпадает с прежним планом | `source_changed`, а не ложный `already_verified` |
| R18 | Администратор восстановил исход unknown по серверным доказательствам | Ref/решение журналированы; success проходит проверку, failed допускает новый attempt |
| R19 | Crash после DB done до удаления staging | После restart удалён только собственный терминальный локальный остаток |
| R20 | В технической папке назначения появился посторонний файл | Утилита не удаляет папку рекурсивно; файл сохранён, остаток отражён в отчёте |

## Проверки эксплуатации

- В режиме URL байты не записываются в локальный staging.
- В staged расход RAM не растёт пропорционально размеру файла; бюджет места
  соблюдается, полный проверенный файл пригоден для повторной загрузки.
- SQLite и собственные файлы переживают пересоздание контейнера с сохранённым томом.
- Второй worker с тем же томом не запускает передачи.
- Лимиты источника общие с действующими SaaS-режимами; назначения — отдельные.
- В UI, событиях, CSV и SQLite отсутствуют OAuth, client secret и signed URL.
- Сравнение итогов выполняется по дереву, размеру и hash, а не по одному счётчику.
- Прежние тесты `python3 -m pytest tests -q` проходят после реализации.

## Как фиксировать результат

Для каждого сценария: версия стенда, безопасный job/attempt ID, способ передачи,
проверенный размер/hash, наблюдаемые HTTP-коды и статусы, результат восстановления
и вывод `passed`/`failed`/`not_run`. Подписанные URL и тела с секретами исключаются.
Сценарий `not_run` остаётся ограничением доказательств, а не условным успехом.

Допуск к пилоту: оба способа прошли базовую передачу и проверку содержимого;
защита существующих файлов подтверждена; R01/R02/R04 не дают ложный успех или
слепой повтор; ошибки, конфликты и ограничения видны в отчёте.
